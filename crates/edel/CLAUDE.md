# The `edel` tool

The one command-line tool of Edel OS and the library `edel::settings`: the workspace's default member, beside `crates/compositor`. Edition 2024, `rust-version = "1.85"`, GPL-3.0-or-later, `publish = false`.

## What belongs here

- Every system function lands here as a subcommand (`edel update`, `edel rollback`, `edel status`, `edel restart`, `edel shutdown`, `edel suspend`, `edel boot` (`mount-data`, `guard`, `mark-good`, `live`), `edel release`, `edel settings`, `edel install`, `edel report`), never as a separate tool: "one tool to learn" (`main.rs`). Add-ons, the live USB and fleet images are built by the same `edel image build`, not by a new builder.
- Settings change only through `edel settings set` and `reset`. Never add a per-domain verb that changes settings (no `edel addon add`), an alias (a second name for a command or a key), telemetry, runtime-loaded code or a plugin API (ADR-008).
- The library target (`lib.rs`, which lists its public modules, 37 on 2026-10-13: `edel::settings`, `edel::features`, `edel::tokens`, `edel::presets` and the rest; three parts since M6.17: the settings format and the desktop's models, always built, and the system's own work, `base`, `install`, `firmware`, `keep`, `scripts`, `services`, `speakers` and the feature file reader (`features/file.rs`, re-exported as `edel::features::*`), behind the `os` feature, which `cli` turns on and Settings takes; `features` itself keeps `DIR` and `is_name` for every part; the format and the models stay one crate until M7.12) is the one parser for settings files and feature files. The compositor (M4.5), shell-ui (M5.1) and Settings (M5.6) link it, so it has no network or signing dependencies: `clap`, `ed25519-dalek`, `flate2`, `sha2` and `ureq` are optional and sit behind the binary's default `cli` feature (ADR-008). CI builds the library with `--no-default-features`; code the library needs never uses them.
- **Stands alone (M8.13):** the library needs only its own crates.io dependencies and the files `edel::places` names, and never depends on a binary of ours (`ci/seams.sh`). The desktop parts take it without the `cli` feature, so they carry none of its network, hashing or signing code, and the compositor and shell-ui without `os` too, so they carry none of the system's own work (M6.17). A test that needs an `os` module in a module that is always built is marked `#[cfg(feature = "os")]`.

## Fast checks

Run the eleven "Rust checks" commands from the root CLAUDE.md before every push. After touching `image.rs`, `run.rs` or `def.rs`, also run `cargo run -- image build images/vm.toml --plan` and the same for `images/container.toml`. Run the tool with `cargo run -- ...`, never a binary left in `target/`: a stale build rejects newer definitions with errors such as "unknown field `cmdline`".

## Layout

- `services.rs` (library, M6.10): `[services]`, a switchable feature on or off by name: `installed` (the feature files in `features::DIR`, read leniently), `switchable`, `problems` (a name that is no switchable feature, with the ones there are; `edel settings set` and `check` refuse it, apply notes it), `off_by_default` (`EDEL_SERVICES_OFF` in os-release), `is_on` (the file's choice, else the image's), `plan` (the runlevel `Step`s that match the choice: a feature off takes out only the services no feature that is on lists, and only switchable features' services are ever touched) and `enabled_in` (what `/etc/runlevels` holds). `machine.rs` plans one `Change::Service` per step: at boot only `rc-update`, later `rc-service` start or stop too. Tested.
- `lib.rs`: the library; `settings.rs`: `settings.toml` format 1, the pages `PAGES` (each under one of the `GROUPS` headings, Desktop, Connections, Devices, Personal and System, M5.32b; `edel settings` and Settings' sidebar list them alike), the key table `KEYS` (path, kind, supported; `Kind::WholeFromTo` (M5.2i) is a whole number in a range, its bounds checked and named in the message), `Kind::AppIds` (M6.1) is a list of Flatpak app ids checked by `apps::is_flatpak_id` (a bad one leaves the whole list out, as `Kind::Hosts` does), the structs, `read` (lenient: unknown keys and wrong values are dropped and reported), `check` (strict, also refuses keys not supported yet) and `read_on_machine` (a newer format reads `settings.toml.v<N>` beside it, else fails).
- `apps.rs` (library, moved from shell-ui in M5.6a): the default apps' installation (M6.2): `INSTALLATION` (`edel`), `APPS_REMOTE` (`edel-apps`), `installation_conf` apps feature's lists; people have, from the `.desktop` files (`dirs`, `data_dirs`, `read_all`, `parse`, `search`, `command`, `pinned`), read leniently without GLib; `FLATHUB_REMOTE`, the one Flathub URL, and `data_dirs` reads `remote_add_args` (`--from` `flatpak_dropped`, written by `read`) by `text` `installation_file`, `DefaultApps` `is_flatpak_id`, the checker of `apps.installed`'s ids (M6.1) (M6.1); `belongs` and `of_window` find the app a `file://` or plain `http://` test repository), `.flatpakrepo`, `--no-gpg-verify` window's app id belongs to, for shell-ui's apps widget and the compositor's title bars. Tested on files in a temp directory. M6.10: `DEFAULT_APP_KEYS` (each role and its exports at `places::DEFAULT_APPS`; `[default_apps]` key), `apps_of_role` (a role's apps in the order `default_app` picks from), `default_app` (the slot's list, `flatpak` app the key names when installed, else the role's first app) and `mime_defaults`, the text of `/etc/xdg/mimeapps.list` from the MIME types each role opens (`MIME_TYPES`), its first line `MIME_COMMENT`.
- `addons.rs` (the tool's, M7.2a, [FEATURES.md](../../docs/FEATURES.md#add-ons-m72a)): add-ons, features with `addon = true` built beside an image. Pure rules, tested without root: `relocate` (`etc/init.d/X` to `places::ADDON_INIT_DIR`, the rest of `/etc` and `/var` to the add-on's own folders under `/usr/lib/edel`), `is_system_cache` and `is_discarded` (left out), `scan`, `diff` and `plan_tree` (what a build keeps), `new_accounts`, `account_clashes` and `collisions` (one path, one owner), `lowerdirs`, `stale_versions`, `fetch_plan` (which add-ons a release has, with a note for each it has not), `Links::plan` (the `/etc` links apply makes and takes out; a machine's own file is never replaced) and `rows` (`edel addon list`). - `guard.rs`: `edel boot guard`, which pets the watchdog until the health files in `EDEL_HEALTH` exist, then confirms the slot and stops the watchdog with the magic close, or lets it reset the machine after `EDEL_HEALTH_TIMEOUT`; with no watchdog at all it restarts the machine itself then, `sync` and the `reboot` system call, as `reboot -f` does, so a hung service cannot hold it up (M1.10). Before either it reads GRUB's environment (`update::boot_env`): when no slot is OK with a try left (`may_retry`, `boot::TRIES`), a restart would only start this slot again, so it stops the watchdog, keeps the machine running, writes why to `places::NO_HEALTHY_SLOT`, which `edel status` prints as `health: ...`, and still confirms the slot should it become healthy later (M6.17), unless developer mode's layer is on (`places::DEVELOPER_NOW`), as then the restart is a safe start without it (M7.1); an environment it cannot read restarts as before. Health names are edel's two (`default-runlevel`, `compositor`, files from `places`) or a feature's own, `places::HEALTH_DIR/NAME` (`health_file`, M1.11); `ImageDef::validate` refuses one no shipped file writes as `$health_dir/NAME`, and at the timeout the guard says which were not reached. It starts on `/dev/watchdog` (softdog when nothing else has loaded, or nothing on linux-virt, which lacks softdog) and takes the first hardware watchdog `/sys/class/watchdog/*/identity` shows once hwdrivers loads one, closing softdog, which a frozen kernel never fires. Until then the kernel's own lockup detectors panic (`softlockup_panic=1 nmi_watchdog=panic` in `boot::WATCHDOG_ARGS`, with `panic=10`), so a kernel that locks up during the boot, before the guard or with no hardware watchdog, costs a try; `calm_lockups` writes 0 to `/proc/sys/kernel/softlockup_panic` and `hardlockup_panic` once the slot is confirmed or the guard stands down, so a running machine only logs a lockup (M6.17). A missing root needs nothing of ours: with `panic=` on the command line Alpine's initramfs exits instead of opening its emergency shell, and the kernel's panic restarts the machine (the A/B test's step 4b, a slot whose `slot.cfg` names a root that does not exist).
- `release.rs`: `release.toml` (format 1, read leniently), ed25519 keys and signatures, `edel release keygen|make|sign|verify`, and `open_checked` (returns `Checked`: the image reader, its sha256 and size), which `edel update` calls before writing a slot. Since M3.8 a list carries `expires` (`sign --expires-in`; since M6.17 `sign` refuses a list with none and no `--expires-in`), and `check_list` refuses a list with no `expires`, and `check_location` refuse an expired list, another channel than `machine_channel()` (`edel::settings::channel`: `updates.channel`, the person's over the machine's, else the image's `EDEL_CHANNEL`, else `stable`) unless `Accept::channel` asks, and plain http unless `Accept::allow_http`; dates are days since 1970 (`parse_date`, `civil_from_days`), with no date crate. `edel release make --base-url URL` names each image by its URL there (a channel manifest served apart from the images, M3.4) and `--out DIR` writes `release.toml` there; with no RELEASE named, `edel update` takes `default_location`, the list of `--channel`'s or the machine's channel at `channel_list` (M5.8c); an image `file` that is a URL is used as it is. `edel update --check` prints `running:` and `available:` for people, then lines a program reads, as `edel status`' are, which stay English (M5.8d: `newer: yes` or `no`, `released: DATE` when the list has one, `size: BYTES` of this system's image in the list; `check_lines`, tested); Settings' Updates page reads them. `version.rs` (library) orders dotted versions (`compare`), a test build before its release (`1-rc1` before `1`, M6.17), which `release::compare_versions` re-exports and Settings uses to tell a newer version from an older one.
- `loader.rs`: the boot loader riding along (M1.8): `loader.toml`, `swap_file` (`.prev`, `.new`, rename) and `update_esp`, which `mark-good` calls once the slot is confirmed.
- `run.rs`: `Runner` (dry run, external tools), kernel filesystem mounts with `MountGuard`, `ensure_nothing_mounted_under`.
- `shell.rs`: the desktop's effect tier for `edel status` (M5.11a, M5.25a): `tier_now` reads `tier` from `/run/edel/session/state.toml` (`tier_of`, tested); status prints it as `effects: lite` while a session runs.

## Conventions

- Today the dependencies are `anyhow`, `serde`, `serde_ignored`, `toml` and `toml_edit` for the library (with `resvg` and `tiny-skia` behind its `icons` feature, and `jpeg-decoder` behind `pictures`), and `clap`, `ed25519-dalek`, `flate2`, `sha2` and `ureq` (rustls with ring, webpki roots) for the command, with no dev-dependencies. The roadmap names the next ones. Every new one, those included, needs a one-paragraph reason in the PR (principle 3) and its `Cargo.lock` change (CI uses `--locked`).
- Release binaries are built by Alpine 3.24's `cargo` package inside `ci/build.sh` (musl), not only by the runner's Rust. Code must build with both. Crates the roadmap marks "check in CI" (the `ed25519-dalek` musl build in M1.6, rustls with the ring provider in M1.7, `serde_ignored` in M2.1) are proven by that step's first CI run.
- Errors: `anyhow` only, no custom error types. Return `Result`, fail with `bail!`, add `.context(...)` or `.with_context(...)`. Messages are lower case, have no final period, quote values with `{:?}` and say what to do: "the image has no /usr/lib/os-release; add one to the files directories". Progress goes to stdout with `println!`; non-fatal problems go to stderr as `warning: ...`. `main` prints a failure as one line, `edel COMMAND: message: cause`, the most specific cause last; a refused write says to run as root (`update::io_failure`). The messages a person meets most are held to their text by tests (M5.28b).
- No `unwrap` outside tests; an `expect` (a few, in `boot.rs`, `tokens.rs` and `presets.rs`) says why it cannot fail. No `unsafe`, no `#[allow]`, no lint config: CI's `clippy -D warnings` and `fmt --check` are the rules.
- Each file opens with a `//!` doc, public items have `///` docs, and comments say why and cite the ADR they implement ("(stateless /etc, ADR-006)"). Imports come in three groups separated by blank lines: `std`, external crates, `crate::`. Use inline format captures (`{FORMAT}`, `{hostname:?}`).

## Rules that protect real machines

- A new command that changes the machine gets a `Need` in `privilege::need` (M6.5): `Admin` for a change an administrator makes, `Password` for one that can break or open the machine (an install, an update, a rollback). doas's rule (`features/machine/etc/doas.d/edel.conf`) lets the admin group run `edel` with no doas password, so the gate is the one check.
- In `edel image build`, and in any other command that has `--plan`, run every external tool through `Runner::run` or `Runner::run_with_input`; print work edel does itself with `Runner::step` and guard it with `if !self.runner.dry_run` or an early return. A dry run changes nothing and needs no root, Alpine or network. `Runner::run` captures no output and treats any non-zero exit as failure, so commands without a dry run, such as `edel update`, call tools with `std::process::Command` directly and check the exit status themselves.
- Image builds use no loop devices and mount no images (`mkfs.ext4 -d`, `mkfs.vfat` with mtools, `sfdisk`, sparse copies at byte offsets). The only mounts are proc, sys and dev from `mount_kernel_fs`, undone by `MountGuard`. Never delete a work directory without `ensure_nothing_mounted_under`: a live bind of `/dev` inside it would delete the host's devices.
- Every image is `/usr`-merged (M7.1): `/bin`, `/sbin` and `/lib` are links into `/usr`, made last in the build, so a feature's files and new code name `/usr/...` paths, and nothing of the system's own lives outside `/usr` but `/etc` (the machine's) and `/boot`. Developer mode's one overlay over `/usr` depends on it; never write into a slot's `/usr` at run time any other way, and never change a live overlay's upper folder: a reset waits for the next start.
- Disk layout: partition 1 is the EFI system partition (`EDEL-ESP`, 64 MiB), 2 is slot A, 3 is slot B, 4 is `edel-data` (64 MiB in the image, grown with `sfdisk` and `partx` on first boot); GRUB and the updater rely on it. No two filesystems a machine can see may share a UUID: slot A gets its own mkfs, and a written slot gets `tune2fs -U random`.
- The grubenv block is exactly 1024 bytes, rewritten in place, and keeps RAUC's names: `ORDER`, `A_OK`, `A_TRY`, `B_OK`, `B_TRY`. GRUB menu entries are numbered because GRUB 2.12 ignores an entry id in `fallback`. `vm.cmdline` is pasted into `grub.cfg`; keep it behind `boot::is_safe_cmdline`.

## Updater rules (M1.1 and every later updater step)

- The running slot comes from the mounted root (partition 2 is A, 3 is B), never from the kernel command line, and the running slot is never written.
- Install switches the target off (`<slot>_OK=0`) before writing it, checks the image's size against the slot, writes it, drops the cache (`blockdev --flushbufs`), checks the write by sha256, then runs `e2fsck -fn`, which changes nothing, and must exit 0. The slot keeps the image's bytes and its file system UUID, never grown (M1.12): GRUB boots a slot by its partition (`root=PARTUUID=`, which `image.rs`'s `partuuid_init` teaches Alpine's initramfs `init` to mount), and `edel install` copies the running slot into slot A byte for byte and checks the copy by sha256.
- With `--unsigned`, IMAGE may be a block device (no CI test uses this today), so size it by seeking to its end (file metadata reports 0 for a device), and hash only the first <image size> bytes of the slot.
- `mark-good` detects a fallback: when ORDER starts with the other slot, that slot is OK and its TRY is 1 or more, GRUB passed over it (GRUB counts a try before starting a slot). An OK slot first with TRY 0 was installed or rolled back to during this boot: it is pending and keeps its place, and only the running slot is confirmed. For a passed-over slot it logs `slot X did not start, so slot Y is running instead; switching slot X off` and sets `X_OK=0`. In every case it then sets ORDER to the running slot first, with `OK=1` and `TRY=0`. It records that fallback in `/data/edel/last-fallback.toml` (format, from, to, date) for shell-ui to show once (M5.9).
- One updater at a time: install, mark-good and rollback take `/run/edel/update.lock` (`update::Lock`, a file holding the pid; a lock whose pid is gone is stale and replaced; the file holds `PID COMMAND`, and a refused command names the holder; `edel settings apply` takes `system.lock` the same way). Mount the EFI system partition only while writing it, on a directory of the process's own (`/run/edel/esp.<pid>`), never in fstab, with `-o noatime,dirsync,iocharset=iso8859-1` (the virt kernel lacks utf8 for FAT; `dirsync` writes each rename of the loader swap at once). Downloads time out after 30 s without a connection or 60 s without a response. Rewrite grubenv in place, as `dd ... bs=1024 count=1 conv=notrunc,fsync` does.

## Formats: strict for builders, lenient on machines

- Every file format has a top-level integer `format`, from version 1. Image definitions are format 2 (`def::FORMAT`, M4.0); feature files are format 1 (`features::FORMAT`); bump it only for a breaking change. Every definition lives in this repository, so the bump converts them in the same PR and refuses the old format (M4.0); migration (`edel migrate`) is for files on machines, such as `settings.toml`.
- Image definitions and presets stay strict (`#[serde(deny_unknown_fields)]`): only CI and the slot that ships them read them.
- Files a machine reads from another release (`release.toml` from M1.6, `settings.toml` from M2.1, feature files) are lenient. Before writing one, read the reader table in [ADR-008](../../docs/ADR-008-features-defaults-and-install.md), section 2. In short: no `deny_unknown_fields`; collect unknown keys with `serde_ignored` and report them; read enum values leniently; write with `toml_edit` so unknown keys and comments survive. Refuse only a format you do not know.
- Once Edel OS is released, a key is never removed or renamed within a format; until then keys are renamed freely, with no old name kept (Alimardon, 2026-10-10; ADR-008). From M2.1 a cargo test checks the structs against the append-only `crates/edel/tests/keys.txt`. A dropped key gets `retired = "VERSION"` in the help table next to the structs (M6.11): it is still parsed, reported as no longer used and refused by `set`, until `edel migrate` drops it at the next format bump.
- Name settings after what the user sees (`services.ssh`, `layout.tiling`). An absent key means the release decides. Resolve every key in one order: user file, machine file, profiles in listed order, preset, release default. Writers never write a default; apply enforces the release default for every absent key, so `reset` really undoes; `edel settings get KEY` prints the value and its layer (ADR-008, M2.3, M5.6, M6.11).

## Must keep working offline

- `cargo test`, `edel image check` and `--plan` need no network. A failed fetch leaves the slot off and the running system untouched.
- `edel update` keeps accepting a local path or a `file://` URL for USB installs next to network URLs (M1.7). USB and offline installs, add-ons included, keep working (M7.2a).
- The boot service `edel-settings` applies only the offline sections of `settings.toml`. Sections that need the network (`[apps]`) run only when a user or Settings calls apply, in the background, never from the boot service (M2.2, M6.1).

## Tests

- Unit tests close each file: `#[cfg(test)] mod tests { use super::*; ... }`. Names are sentences in snake_case: `rejects_unknown_fields`, `grub_counts_every_try`. `tests/` holds `keys.txt`, the append-only list of settings file keys that `settings.rs` tests read, and `format1/`, `main`'s format-1 definitions from before M4.0 that `def.rs` tests rebuild from features; there are no integration tests.
- Put logic in small pure functions that take text and numbers, so tests need no root, disk, Alpine or network; what needs Alpine, root or a VM is proven by the `ci/` scripts in CI. `def.rs` tests merge a `const VM: &str` with in-memory features and vary it with `.replace(...)`.
- A test that needs files works under `std::env::temp_dir()` in a directory named after that test and the process id (`edel-copy-sparse-<pid>` in `copies_into_place_and_keeps_holes`), because cargo runs tests in parallel threads of one process, and removes it afterwards.
