# The `edel` tool

The one command-line tool of Edel OS and the library `edel::settings`: the workspace's default member, beside `crates/compositor`. Edition 2024, `rust-version = "1.85"`, GPL-3.0-or-later, `publish = false`.

## What belongs here

- Every system function lands here as a subcommand (`edel update`, `edel rollback`, `edel status`, `edel boot` (`mount-data`, `guard`, `mark-good`, `live`), `edel release`, `edel settings`, `edel install`, `edel report`), never as a separate tool: "one tool to learn" (`main.rs`). Add-ons, the live USB and fleet images are built by the same `edel image build`, not by a new builder.
- Settings change only through `edel settings set` and `reset`. Never add a per-domain verb that changes settings (no `edel addon add`), an alias (a second name for a command or a key), telemetry, runtime-loaded code or a plugin API (ADR-008).
- The library target (`lib.rs`: `edel::settings`, `edel::features`, `edel::install`, `edel::keyboard`, `edel::presets`, `edel::shortcuts` and `edel::tokens`) is the one parser for settings files and feature files. The compositor (M4.5), shell-ui (M5.1) and Settings (M5.6) link it, so it has no network or signing dependencies: `clap`, `ed25519-dalek`, `flate2`, `sha2` and `ureq` are optional and sit behind the binary's default `cli` feature (ADR-008). CI builds the library with `--no-default-features`; code the library needs never uses them.

## Fast checks

Run the eight "Rust checks" commands from the root CLAUDE.md before every push. After touching `image.rs`, `run.rs` or `def.rs`, also run `cargo run -- image build images/vm.toml --plan` and the same for `images/container.toml`. Run the tool with `cargo run -- ...`, never a binary left in `target/`: a stale build rejects newer definitions with errors such as "unknown field `cmdline`".

## Layout

- `lib.rs`: the library; `settings.rs`: `settings.toml` format 1, the key table `KEYS` (path, kind, supported), the structs, `read` (lenient: unknown keys and wrong values are dropped and reported), `check` (strict, also refuses keys not supported yet) and `read_on_machine` (a newer format reads `settings.toml.v<N>` beside it, else fails).
- `apps.rs` (library, moved from shell-ui in M5.6a): the apps people have, from the `.desktop` files (`dirs`, `data_dirs`, `read_all`, `parse`, `search`, `command`, `pinned`), read without GLib; `belongs` and `of_window` find the app a window's app id belongs to, for shell-ui's apps widget and the compositor's title bars. Tested on files in a temp directory.
- `app_icons.rs` (library, feature `icons`, moved from shell-ui in M5.6a): apps' icons from the icon themes (hicolor, then `/usr/share/pixmaps`): `find` a PNG at least as big as asked, else the SVG, else the biggest smaller PNG; `draw` it at a size (PNGs through tiny-skia, SVGs through `icons::svg_pixmap`); `Icons` keeps each drawn once; `Picture` is tiny-skia's pixmap.
- `icons.rs` (library, feature `icons`, M5.5d): the shell's own icons, one SVG each in `design/icons/` (`menu`, `app-generic`, `layout-floating`, `layout-tiling`, `minimize`, `maximize`, `restore`, `close`, and Settings' `page-layout`, `page-displays` (M5.7a), `page-sound` (M5.7b), `page-network`, `page-bluetooth` and `lock` (M5.8a), `page-about`, `search`, `copy`, `check` and `back`, M5.6a, and the Updates page's big `status-ok`, `status-new`, `status-restart`, `status-problem` and `status-sync`, M5.8d), built in (`BUILT_IN`; a test fails when a file there is not); `mask` draws one in black at a size, its alpha the coverage, `draw` in a token's colour, and `svg_pixmap` any SVG, which app icons use too. The compositor, shell-ui and Settings turn the feature on; the command does not. Each is a shape in black, coloured by the part that draws it, so a changed file changes every place that shows it at the next build. Tested. The status area's and quick settings' (M5.9a): `net-wired`, `net-wifi-1` to `3`, `net-offline`, `airplane`, `volume-muted`, `volume-low`, `volume-medium`, `volume-high`, `battery`, `battery-level`, `battery-bolt`, `moon`, `gear`, `chevron-right`, `chevron-down`.
- `tokens.rs` (library, moved from the compositor in M5.1b): the design tokens from `design/tokens.toml`, built in, read leniently by `Tokens::read` and strictly by `check`; the panel's drawing sizes (`size.panel_text_small`, `panel_control`, `panel_icon` and `panel_glyph`, M5.29: the date's text, a button's height, an app's icon in it and the shell's own icons); corner radii for windows, menus and controls (`radius_window`, `radius_menu`, `radius_control`, M5.5e) and one shadow (`colour.shadow`, `size.shadow_blur`, `size.shadow_offset`); apps' surfaces (`colour.window`, `card`, `line` and `accent_text`, `size.radius_small` and `size.text`, M5.6a), the hairline round windows and panels (`colour.edge`), which Settings is drawn with and GTK's `window_bg_color`, `view_bg_color`, `card_bg_color`, `popover_bg_color` and `dialog_bg_color` take; the compositor (`edel_compositor::tokens` re-exports it) and shell-ui read them through it. `[colour.light]` holds the light scheme's colours (M5.5c): `Scheme` (`light`, else dark, as `auto` is in this release) and `load(scheme)` give the image's tokens in either, every colour in both (`check` wants each). `Tokens::gtk_css(dark, light)` (M5.5b) writes GTK's named colours as `@define-color` lines, the light ones inside `@media (prefers-color-scheme: light)`, which GTK 4.22 matches when the settings portal says light; the shell feature ships them as `/usr/share/edel/gtk.css` (`GTK_CSS`), and a test fails when that file differs from the tokens (`EDEL_WRITE_GTK_CSS=1` rewrites it); `Colour::hex` writes `#rrggbb`. `Tokens::site_css(dark, light)` (M8.10a) writes the docs site's `--edel-*` custom properties, with the same colour roles as GTK's (the page as a view, the sidebar as a window), and a test holds `docs/theme/tokens.css` to it (`EDEL_WRITE_DOCS=1 cargo test -p edel site_css`).
- `presets.rs` (library, M5.1c): the layout presets from `presets/NAME.toml`, built in through `BUILT_IN` in the order people see them, Classic, Mac-like, Windows-like, Hive (a new preset is a file and a line, its name in `system::PRESETS`; `[session] start` (M5.7b) lists the commands the compositor starts with the session and is left out by every preset, so `SESSION_START` (pipewire, wireplumber) is the one list; Settings draws its card from the file); `check` reads one strictly (format 1, no unknown key, 1 to `MOST_WORKSPACES` workspaces (M5.2a), one panel per edge, widget names that are names) and the tests check every one; `named` gives the preset `layout.preset` names, or Classic with a note. `[quick] tiles` (M5.9a, `Quick`, `check_quick`): the tiles of the panel's quick settings, names from `TILES` (shell-ui has one tile each, and its tests fail when they differ), none twice; `DEFAULT_TILES` for a preset that says nothing.
- `sound.rs` (library, M5.7b): sound devices as PipeWire reports them, through `wpctl` (WirePlumber): `parse` reads `wpctl status` into `Devices` (sinks and sources, each `Device` with id, name, whether it is in use, volume in percent and mute; only the Audio part, any later section or column skipped), `read` runs it, `volume_args`, `mute_args`, `default_args` and `command_line` build the commands Settings runs and copies, `set_volume`, `set_mute` and `set_default` run them, in the words of `docs/MESSAGES.md`. Std only. The volume and the chosen device are the sound system's own state, not settings file keys. Tested on a sample of the status text.
- `tool.rs` (library, M5.8a): `run` runs a program with no input for at most a time, reading both pipes while it runs, and kills it when the time is up (`Done`: status, `timed_out`, output, error); `command_line` writes a program and its arguments as one quoted line for Copy as command. `nmcli` and `bluetoothctl` go through it, because `bluetoothctl` waits for ever for a `bluetoothd` that is not running. Std only. Tested, a killed `sh` and its `sleep` included.
- `network.rs` (library, M5.8a): the network as NetworkManager reports it, through `nmcli -t`: `fields` (the `:` and `\` escapes), `parse_status`, `parse_devices`, `parse_connections`, `parse_wifi` (one entry for each name, the one in use first, then the strongest; hidden networks left out), `parse_details`, `Snapshot` (`summary` says how the machine is connected: a cable wins over Wi-Fi), `read`, `details`, `rescan`, and `set_wifi`, `join` (a remembered network by name, a new one with its password; a new network that failed is forgotten again), `forget` and `leave`, with `radio_args`, `join_args`, `up_args`, `forget_args`, `leave_args` and `command_line` for Copy as command, in the words of `docs/MESSAGES.md`. Std only. The connections and passwords are NetworkManager's own state, never settings file keys (ADR-006). Tested on samples of `nmcli -t` text. `radios_args` and `set_radios` (M5.9a) switch every radio, for the Airplane mode tile.
- `bluetooth.rs` (library, M5.8a): Bluetooth as BlueZ reports it, through `bluetoothctl`'s one-command form: `parse_list`, `parse_show` (`Adapter`), `parse_devices`, `parse_info` (`Device`, its `Kind` from BlueZ's icon, nameless ones hidden by `arrange` unless paired), `kernel_has_adapter` (`/sys/class/bluetooth`, to tell no Bluetooth from a `bluetoothd` that is not answering), `read` (no adapter is a snapshot with none, not an error), `set_power`, `scan` (10 s), `pair` (agent `NoInputNoOutput`, then trust, then connect), `connect`, `disconnect` and `remove`, with their `*_args` and `command_line`. Colour codes `bluetoothctl` writes are stripped. Std only. The pairings are BlueZ's own, never settings file keys. Tested on samples of its text. `adapter` (M5.9a) reads the adapter alone, two calls, for the panel's quick settings.
- `power.rs` (library, M5.8b): the battery and the power source as UPower reports them, from one `upower -d`: charge, state, time left, plugged in, and every device UPower lists (ADR-011: whatever it lists, a paired phone's later); no battery is simply plugged in; Settings' Power page reads it, the panel's battery will (M5.9). `battery_line` (M5.9a) is the quick settings' line, "82 percent, 4 hours 10 minutes left".
- `users.rs` (library, M5.8b): the people with an account, from `/etc/passwd` and `/etc/group` (login name, full name, administrator or not, home, shell; `ADMIN_GROUP`, moved here from `machine.rs`), never `/etc/shadow`; changing people stays `edel settings`' `users.NAME.*` keys.
- `i18n.rs` (library, M5.24a): the words people read, in their language. `tr("...")` gives a word in the language `region.language` names (the person's over the machine's), `trf("... {name} ...", &[("name", value)])` fills names after translating, and `n_("...")` marks a word in a constant or table that `tr` translates where it is shown; each part calls `init(PART)` once at start, which reads `LANG/PART.po` under `places::LOCALE_DIR` (`pt_BR`, else `pt`) with the small `.po` reader here (the Settings app's `init` also reads `edel`'s catalogue under its own). A test gathers the marked words of shell-ui and Settings into `po/shell-ui.pot` and `po/settings.pot`, and `main.rs`'s gathers everything marked under `src` plus the help texts of the command table into `po/edel.pot` (M5.24b); they fail when a committed one differs (`EDEL_WRITE_DOCS=1 cargo test --no-fail-fast -p edel i18n` writes them). A word more than one part shows (the pages' titles and descriptions, the presets' names) is marked here and lives in `po/edel.pot` only. Every message `edel` prints for people goes through `tr` or `trf` (`trf("could not read {path}", &[("path", &shown)])`, never `format!` around English); leave machine-read lines (TOML output, `running:`, `change:`, key names, paths) and the boot services' log lines alone. clap's help is translated at start by `translated` in `main.rs`, so a doc comment on a command or option needs no mark. `with_catalogue` runs a test in a made-up language. Only literal words are found: never pass `tr` a variable, and never build a sentence from translated pieces.
- `session_log.rs` (library, M5.28a): the desktop session's log, one per person in `places::person_state_dir()` (`~/.local/state/edel/session.log`, the session before's beside it as `session.old.log`). `start` moves the old one aside and opens the new one for the compositor, saying whether the session before ended without `ENDED`, its last line; `people`, `ended_badly`, `runs_as_owner_of` and `tail` are what `edel report` and `edel status` read it with.
- `shortcuts.rs` (library, M5.13a): `ACTIONS` (name, default keys, whether it is a way out, what it does; append only, as each name is a settings file key), `parse` and `normalize` (`Kind::Keys` in `settings.rs`: modifiers and one key, written `Super+Ctrl+Alt+Shift+KEY`), `check` (strict: unknown actions, two on one key, a way out unbound; `system::check` and `system::set` call it), `resolve` (lenient, for the compositor and later Settings) and `markdown`, which `docs/SHORTCUTS.md` must equal (`EDEL_WRITE_DOCS=1 cargo test -p edel shortcuts` writes it).
- `keyboard.rs` (library, M5.21a): `region.keyboard`: `parse` (layouts as xkb names them, each with a variant if wanted, at most `MOST_LAYOUTS`), `known` (the layouts and variants in xkeyboard-config's list, `RULES`), `normalize` (the one spelling, checked against that list when the machine has it; `Kind::Keyboard` in `settings.rs`) and `xkb_names` (the layout and variant lists the compositor gives xkb). Tested with a sample of the list.
- `install.rs` (library): the install plan, `edel::install::Plan`: the target disk's model, size and partitions (`sda3: Windows (NTFS, 420 GB)`) and the layout to write; Settings' installer page shows the same plan (M6.6a).
- `installer.rs`: `edel install DISK --settings FILE` (M2.4; slots of `install::SLOT_MIB`, 4096 MiB, whatever the running slot's size, the copied slot grown with `resize2fs`, M3.3b): refuses the running disk, a mounted disk and a settings file with any problem; shows the plan for `--plan`, before asking for the disk's name on a terminal, and before exit 3 with neither a terminal nor `--yes`; then partitions with `boot::Layout`, copies the running slot to slot A (`e2fsck -fp`, `tune2fs -U random`), writes the ESP from `/usr/lib/edel/boot` with an initial grubenv, and creates `edel-data` holding the settings file. `TOOLS` lists the tools it runs; a test holds `images/vm.toml` to it.
- `live.rs`: `edel boot live` (M3.6), run at boot by the login feature's `edel-live`: when the running disk is removable (`report::is_removable`) or nobody has an account (`machine::has_person`), it adds the system account `live` (`machine::add_live_account`: `*` for no password, the seat) and writes `/run/edel/greetd.toml`, greetd's config with an `initial_session` running `/usr/libexec/edel-session` as `live` (`toml_edit`, so a session the slot's file names is replaced, never doubled); otherwise it says the greeter asks. Tested.
- `places.rs` (library, M5.25a, M5.27; ADR-010): every place Edel OS keeps a file, each root (`/data`, `/run/edel`, `/usr/share/edel`) written once in a macro: the settings file's name `SETTINGS` with `FORMER_SETTINGS` (`found` reads a file by a former name, `is_settings_name` for watchers), `machine_settings`, `slot_settings`, `etc_settings`, `person_dir`, `person_settings`, and constants for the data partition, the session's files, the guard's files, the slot's share directory and the ESP's; `shell_vars` and `shell_file` write them as shell variables, which a test holds `ci/names.sh` to and `edel image build` writes to `/usr/share/edel/places.sh` (`PLACES_SH`); tests fail when the settings file's name is written anywhere else. `ci/one-place.sh` checks the rest of the places.
- `completion.rs` (M5.26): `bash`, edel's tab completion written from the command table (`cli_command` in `main.rs`) and the key table: commands and long options per command path, a key one part at a time (sections from `system::PAGES`, the shortcut actions in full), values after `=` for flags and listed values; it reads `COMP_LINE`, so it needs no helper library; `edel image build` writes it to `PATH` in every bootable image; a test runs it in bash.
- `report.rs`: `edel report` (M3.3b): TOML on standard output with `format = 1`, the version, the kernel, `started` (the line `edel-boot-ok` keeps in `/run/edel/started`), `memory_in_use_mib`, `features` and `feature_notes` (the feature files in `/usr/share/edel/features/`, read leniently, M4.0), `dmesg`, `system_log` (the last lines of `places::SYSTEM_LOG`), one `[[pci]]` table per device from `/sys/bus/pci/devices` (address, vendor, device, class, driver) and one `[[sessions]]` table per desktop session log (person, path, `ended`, `last_lines`; the person running it, or for root everyone under `/home`, M5.28a); `pointers` gives `edel status` its `logs:` lines when the last boot fell back or a session ended without closing; no tool beyond busybox; `--esp` writes it to `/EFI/edel/report.toml` instead (`update::write_beside_grubenv`, under the update lock), as the laptop stick's `edel-report` service does at every boot (M3.4).
- `main.rs`: the clap derive CLI and its dispatch. Doc comments on variants and fields are the `--help` text: write them for users. A test writes the docs site's command reference, `docs/guide/commands.md`, from this table and fails when the file differs (`EDEL_WRITE_DOCS=1 cargo test -p edel command_reference`, M8.10a); hidden commands stay off it.
- `features.rs` (library, M4.0): feature files, `features/NAME.toml`: `Feature`, `Services` (by runlevel), `read` (lenient, returns notes for what it skipped, for readers on a machine) and `check` (strict, for the build and `image check`; `programs` must be names and need a `why`); [docs/FEATURES.md](../../docs/FEATURES.md).
- `def.rs`: image definitions, format 2 (`ImageDef`, `FORMAT`): `feature_dirs` (beside the definition, and the repository's beside `images/`), `find_features` (every feature file there, checked strictly), `ImageDef::merge` (the listed features in order: packages, services, modules, health and mkinitfs features as sets, and every refusal) and validation; tests rebuild main's format-1 definitions from `tests/format1/`.
- `image.rs`: `edel image build`; `Build::run` calls `prepare_root`, `install_packages` (which records the package list), `copy_files` (each feature's `features/NAME/`, then `--files`), `install_features` (each feature file to `/usr/share/edel/features/`), `install_programs` (in bootable images, each listed feature's `programs` from beside the running `edel` to `/usr/bin`, M4.2b), `enable_services`, `configure` (os-release through `with_version`), then `pack_container` or `pack_vm`. `--apk-cache DIR` shares one package index between the images of a build; only the first fetches it.
- `boot.rs`: the A/B disk layout and `grub.cfg` (`modules=` comes from the features).
- `grubenv.rs`: GRUB's 1024-byte environment block and the `Slot` type, shared by `boot.rs` and `update.rs`.
- `machine.rs`: `edel settings` (M2.2, M2.3, M5.25a): `pages` (the command alone), `get` (a key or a page, each value with its source, a person's own file first for what the desktop reads, or `--toml`), `set` (several `KEY=VALUE`, all checked before any is written), `reset`, `apply` (the machine's file; it first renames a file by a former name and links `/etc/edel/` to it, `settle_names`), `import FILE` (applies FILE and keeps it as the machine's), `diff`, `export` (begins with `EXPORT_HEADER`); `plan` (pure) turns the file and a `Machine` snapshot into `Change`s, which diff prints and apply executes; seeds `/data/edel/settings.toml` on first boot (`EDEL-SEED` volume, the ESP's `/EFI/edel/settings.toml`, the slot's `/usr/share/edel/settings.toml`), applies the hostname, users (busybox `adduser`, the `admin` group, `*` for no password, never `!`; where a `seat` group exists, the people in the file and the greeter's account `greetd` join it, M4.2b), `~/.ssh/authorized_keys` and the developer flag `/data/edel/developer`; a user's home belongs to the user, so `read_keys` opens `authorized_keys` with `O_NOFOLLOW | O_NONBLOCK` and takes only a regular file the user owns, up to 1 MiB, and `write_keys` writes it in a shell running as the user, never as root; `keep_as_machine_file` and `seed` write through a rename, the seed only when this release can read it; pure helpers for passwd, group and shadow lines; `describe` builds the export; set and unset edit through `system::set` and `system::unset` (`toml_edit`, byte for byte) and never apply.
- `update.rs`: `edel update`, `edel rollback`, `edel status` and `edel boot mark-good` (status ends each slot's line with its `VERSION_ID`, read from the other slot with `debugfs`, or `empty`); pure transitions (`before_install`, `after_install`, `confirm`, `roll_back`) and slot discovery (`find_disk`, tested on a fake sysfs tree).
- `data.rs`: `edel boot mount-data`, which grows the data partition on first boot, mounts it at `/data` and overlays `/etc` (merging new system users first), binds `/home`, `/var` and `/root` onto it after topping up `/data/var` from the slot, and mounts `/tmp` as tmpfs.
- `guard.rs`: `edel boot guard`, which pets the watchdog until the health files in `EDEL_HEALTH` exist, then confirms the slot and stops the watchdog with the magic close, or lets it reset the machine after `EDEL_HEALTH_TIMEOUT`; with no watchdog at all it restarts the machine itself then, `sync` and the `reboot` system call, as `reboot -f` does, so a hung service cannot hold it up (M1.10). Health names are edel's two (`default-runlevel`, `compositor`, files from `places`) or a feature's own, `places::HEALTH_DIR/NAME` (`health_file`, M1.11); `ImageDef::validate` refuses one no shipped file writes as `$health_dir/NAME`, and at the timeout the guard says which were not reached. It starts on `/dev/watchdog` (softdog when nothing else has loaded, or nothing on linux-virt, which lacks softdog) and takes the first hardware watchdog `/sys/class/watchdog/*/identity` shows once hwdrivers loads one, closing softdog, which a frozen kernel never fires.
- `release.rs`: `release.toml` (format 1, read leniently), ed25519 keys and signatures, `edel release keygen|make|sign|verify`, and `open_checked` (returns `Checked`: the image reader, its sha256 and size), which `edel update` calls before writing a slot. Since M3.8 a list carries `expires` (`sign --expires-in`), and `check_list` and `check_location` refuse an expired list, another channel than `machine_channel()` (`edel::settings::channel`: `updates.channel`, the person's over the machine's, else the image's `EDEL_CHANNEL`, else `stable`) unless `Accept::channel` asks, and plain http unless `Accept::allow_http`; dates are days since 1970 (`parse_date`, `civil_from_days`), with no date crate. `edel release make --base-url URL` names each image by its URL there (a channel manifest served apart from the images, M3.4) and `--out DIR` writes `release.toml` there; with no RELEASE named, `edel update` takes `default_location`, the list of `--channel`'s or the machine's channel at `channel_list` (M5.8c); an image `file` that is a URL is used as it is. `edel update --check` prints `running:` and `available:` for people, then lines a program reads, as `edel status`' are, which stay English (M5.8d: `newer: yes` or `no`, `released: DATE` when the list has one, `size: BYTES` of this system's image in the list; `check_lines`, tested); Settings' Updates page reads them. `version.rs` (library) orders dotted versions (`compare`), which `release::compare_versions` re-exports and Settings uses to tell a newer version from an older one.
- `loader.rs`: the boot loader riding along (M1.8): `loader.toml`, `swap_file` (`.prev`, `.new`, rename) and `update_esp`, which `mark-good` calls once the slot is confirmed.
- `run.rs`: `Runner` (dry run, external tools), kernel filesystem mounts with `MountGuard`, `ensure_nothing_mounted_under`.
- `shell.rs`: the desktop's effect tier for `edel status` (M5.11a, M5.25a): `tier_now` reads `tier` from `/run/edel/session/state.toml` (`tier_of`, tested); status prints it as `effects: lite` while a session runs.

## Conventions

- Today the dependencies are `anyhow`, `serde`, `serde_ignored`, `toml` and `toml_edit` for the library (with `resvg` and `tiny-skia` behind its `icons` feature), and `clap`, `ed25519-dalek`, `flate2`, `sha2` and `ureq` (rustls with ring, webpki roots) for the command, with no dev-dependencies. The roadmap names the next ones. Every new one, those included, needs a one-paragraph reason in the PR (principle 3) and its `Cargo.lock` change (CI uses `--locked`).
- Release binaries are built by Alpine 3.24's `cargo` package inside `ci/build.sh` (musl), not only by the runner's Rust. Code must build with both. Crates the roadmap marks "check in CI" (the `ed25519-dalek` musl build in M1.6, rustls with the ring provider in M1.7, `serde_ignored` in M2.1) are proven by that step's first CI run.
- Errors: `anyhow` only, no custom error types. Return `Result`, fail with `bail!`, add `.context(...)` or `.with_context(...)`. Messages are lower case, have no final period, quote values with `{:?}` and say what to do: "the image has no /usr/lib/os-release; add one to the files directories". Progress goes to stdout with `println!`; non-fatal problems go to stderr as `warning: ...`. `main` prints a failure as one line, `edel COMMAND: message: cause`, the most specific cause last; a refused write says to run as root (`update::io_failure`). The messages a person meets most are held to their text by tests (M5.28b).
- No `unwrap` outside tests; the one `expect` (in `boot.rs`) says why it cannot fail. No `unsafe`, no `#[allow]`, no lint config: CI's `clippy -D warnings` and `fmt --check` are the rules.
- Each file opens with a `//!` doc, public items have `///` docs, and comments say why and cite the ADR they implement ("(stateless /etc, ADR-006)"). Imports come in three groups separated by blank lines: `std`, external crates, `crate::`. Use inline format captures (`{FORMAT}`, `{hostname:?}`).

## Rules that protect real machines

- In `edel image build`, and in any other command that has `--plan`, run every external tool through `Runner::run` or `Runner::run_with_input`; print work edel does itself with `Runner::step` and guard it with `if !self.runner.dry_run` or an early return. A dry run changes nothing and needs no root, Alpine or network. `Runner::run` captures no output and treats any non-zero exit as failure, so commands without a dry run, such as `edel update`, call tools with `std::process::Command` directly and check the exit status themselves.
- Image builds use no loop devices and mount no images (`mkfs.ext4 -d`, `mkfs.vfat` with mtools, `sfdisk`, sparse copies at byte offsets). The only mounts are proc, sys and dev from `mount_kernel_fs`, undone by `MountGuard`. Never delete a work directory without `ensure_nothing_mounted_under`: a live bind of `/dev` inside it would delete the host's devices.
- Disk layout: partition 1 is the EFI system partition (`EDEL-ESP`, 64 MiB), 2 is slot A, 3 is slot B, 4 is `edel-data` (64 MiB in the image, grown with `sfdisk` and `partx` on first boot); GRUB and the updater rely on it. No two filesystems a machine can see may share a UUID: slot A gets its own mkfs, and a written slot gets `tune2fs -U random`.
- The grubenv block is exactly 1024 bytes, rewritten in place, and keeps RAUC's names: `ORDER`, `A_OK`, `A_TRY`, `B_OK`, `B_TRY`. GRUB menu entries are numbered because GRUB 2.12 ignores an entry id in `fallback`. `vm.cmdline` is pasted into `grub.cfg`; keep it behind `boot::is_safe_cmdline`.

## Updater rules (M1.1 and every later updater step)

- The running slot comes from the mounted root (partition 2 is A, 3 is B), never from the kernel command line, and the running slot is never written.
- Install switches the target off (`<slot>_OK=0`) before writing it, checks the image's size against the slot, writes it, drops the cache (`blockdev --flushbufs`), checks the write by sha256, then runs `e2fsck -fn`, which changes nothing, and must exit 0. The slot keeps the image's bytes and its file system UUID, never grown (M1.12): GRUB boots a slot by its partition (`root=PARTUUID=`, which `image.rs`'s `partuuid_init` teaches Alpine's initramfs `init` to mount), and `edel install` copies the running slot into slot A byte for byte and checks the copy by sha256.
- With `--unsigned`, IMAGE may be a block device (no CI test uses this today), so size it by seeking to its end (file metadata reports 0 for a device), and hash only the first <image size> bytes of the slot.
- `mark-good` detects a fallback: when ORDER starts with the other slot, that slot is OK and its TRY is 1 or more, GRUB passed over it (GRUB counts a try before starting a slot). An OK slot first with TRY 0 was installed or rolled back to during this boot: it is pending and keeps its place, and only the running slot is confirmed. For a passed-over slot it logs `slot X did not start, so slot Y is running instead; switching slot X off` and sets `X_OK=0`. In every case it then sets ORDER to the running slot first, with `OK=1` and `TRY=0`. It records that fallback in `/data/edel/last-fallback.toml` (format, from, to, date) for shell-ui to show once (M5.9).
- One updater at a time: install, mark-good and rollback take `/run/edel/update.lock` (`update::Lock`, a file holding the pid; a lock whose pid is gone is stale and replaced; the file holds `PID COMMAND`, and a refused command names the holder; `edel settings apply` takes `system.lock` the same way). Mount the EFI system partition only while writing it, on a directory of the process's own (`/run/edel/esp.<pid>`), never in fstab, with `-o noatime,dirsync,iocharset=iso8859-1` (the virt kernel lacks utf8 for FAT; `dirsync` writes each rename of the loader swap at once). Downloads time out after 30 s without a connection or 60 s without a response. Rewrite grubenv in place, as `dd ... bs=1024 count=1 conv=notrunc,fsync` does.

## Formats: strict for builders, lenient on machines

- Every file format has a top-level integer `format`, from version 1. Image definitions are format 2 (`def::FORMAT`, M4.0); feature files are format 1 (`features::FORMAT`); bump it only for a breaking change. Every definition lives in this repository, so the bump converts them in the same PR and refuses the old format (M4.0); migration (`edel migrate`) is for files on machines, such as `settings.toml`.
- Image definitions and presets stay strict (`#[serde(deny_unknown_fields)]`): only CI and the slot that ships them read them.
- Files a machine reads from another release (`release.toml` from M1.6, `settings.toml` from M2.1, feature files) are lenient. Before writing one, read the reader table in [ADR-008](../../docs/ADR-008-features-defaults-and-install.md), section 2. In short: no `deny_unknown_fields`; collect unknown keys with `serde_ignored` and report them; read enum values leniently; write with `toml_edit` so unknown keys and comments survive. Refuse only a format you do not know.
- A key is never removed or renamed within a format. From M2.1 a cargo test checks the structs against the append-only `crates/edel/tests/keys.txt`. A dropped key gets `retired = "VERSION"` in the help table next to the structs (M6.11): it is still parsed, reported as no longer used and refused by `set`, until `edel migrate` drops it at the next format bump.
- Name settings after what the user sees (`services.ssh`, `layout.tiling`). An absent key means the release decides. Resolve every key in one order: user file, machine file, profiles in listed order, preset, release default. Writers never write a default; apply enforces the release default for every absent key, so `reset` really undoes; `edel settings get KEY` prints the value and its layer (ADR-008, M2.3, M5.6, M6.11).

## Must keep working offline

- `cargo test`, `edel image check` and `--plan` need no network. A failed fetch leaves the slot off and the running system untouched.
- `edel update` keeps accepting a local path or a `file://` URL for USB installs next to network URLs (M1.7). USB and offline installs, add-ons included, keep working (M7.2a).
- The boot service `edel-settings` applies only the offline sections of `settings.toml`. Sections that need the network (`[apps]`) run only when a user or Settings calls apply, in the background, never from the boot service (M2.2, M6.1).

## Tests

- Unit tests close each file: `#[cfg(test)] mod tests { use super::*; ... }`. Names are sentences in snake_case: `rejects_unknown_fields`, `grub_counts_every_try`. `tests/` holds `keys.txt`, the append-only list of settings file keys that `settings.rs` tests read, and `format1/`, `main`'s format-1 definitions from before M4.0 that `def.rs` tests rebuild from features; there are no integration tests.
- Put logic in small pure functions that take text and numbers, so tests need no root, disk, Alpine or network; what needs Alpine, root or a VM is proven by the `ci/` scripts in CI. `def.rs` tests merge a `const VM: &str` with in-memory features and vary it with `.replace(...)`.
- A test that needs files works under `std::env::temp_dir()` in a directory named after that test and the process id (`edel-copy-sparse-<pid>` in `copies_into_place_and_keeps_holes`), because cargo runs tests in parallel threads of one process, and removes it afterwards.
