# Roadmap

**Status:** Proposed
**Date:** 2026-10-02
**Deciders:** Alimardon (order and vetoes), Claude (execution and defaults)

The plan from phase 0 (a base that boots, updates and rolls back in CI) to a first public release and beyond. It follows the ranked [design principles](DESIGN-PRINCIPLES.md) and the decisions in ADR-002 to ADR-008. The guiding idea is **fewest parts**: one tool (`edel`, inside the image and in CI), one file format (TOML with a format number), one image pipeline (`edel image build`, also for the live USB, add-ons and fleet images), one update path (a whole slot, carrying the bootloader; add-ons ride the same path), one file that describes a machine (`settings.toml`, which also holds the shell, output and update settings the compositor and shell-ui watch). Every milestone says which parts exist after it and which were deliberately not added.

## How this roadmap is used

- Work starts when Alimardon says go. Claude then works through it step by step while Alimardon is away: one branch and one PR per step, merged when CI is green, then the box is ticked here; a docs PR later moves ticked steps to [ROADMAP-DONE.md](ROADMAP-DONE.md), so this file holds what is still to do and the next step starts.
- Each step is a few hundred lines and ends with **Done when:** a check CI runs (cargo tests, a QEMU boot with a line on the serial console, a screenshot pixel check, a container run). Claude has no hardware; Alimardon's trials on their laptops are the only hardware feedback and arrive as comments and `edel report` files.
- When a step turns out wrong or too big, Claude changes the plan in place (splits, reorders, rewrites "Done when") and says so under "Changes to the plan" at the end, dated.
- Open questions are not waited on. Claude takes the default listed under "Decisions taken by default" and lists it there; Alimardon overrules by commenting in the project. They can reorder or veto anything.
- Things that always wait for Alimardon's own words: anything outside this repository (new repositories, accounts, services, repository settings such as branch protection), spending money (runners, storage, domains, devices), publishing to the public (a release, a pre-release, a website, a registry), deleting data, and changing the license.
- Package names, crate names and versions marked "check in CI" are from memory; the first CI run of that step verifies them and the step's notes are corrected afterwards.

## M1 (phase 1, now): One update path, finished

**Goal:** a VM installs a signed, gzip-compressed update straight from a URL, keeps `/home`, `/var` and its own `/etc` changes across the update, comes back on the old slot when the new one hangs (not only when it crashes), can be rolled back by hand, and the bootloader rides along in the same update. Alimardon can run `edel update install https://.../release.toml` on a VM and watch `edel update status`.

**Why first:** Reliable is principle 1, and every later feature is installed, copied and rolled back through this path. Today an update would erase the user's data.

**Depends on:** nothing. **Steps, in the order Claude does them next:**

Finished steps of this milestone: [ROADMAP-DONE.md](ROADMAP-DONE.md#m1-phase-1-now-one-update-path-finished).

**Parts after M1:** Linux kernel, Alpine base (busybox, OpenRC, apk), GRUB, `edel`. **Deliberately not added:** RAUC, ostree, systemd, a watchdog daemon, a separate update agent, an apk repository of our own, delta or zstd updates, LUKS, an initramfs change.

**Principles check:** Reliable drove the data partition, the guard, signing, rollback by hand and the loader swap after confirmation; Simple kept one tool, one partition layout and one standard file for image facts; Efficient won gzip and the shrunken image but lost the per-boot grubenv write to Reliable.

## M2 (phase 1, now): One file describes and installs a machine

**Goal:** `edel settings export` on one VM and `edel settings apply` on another give the same users, hostname and ssh keys; a blank disk becomes an Edel machine from a settings file; CI tests a fresh install, then an update and a rollback on the installed disk, as principle 1 requires. All on a VM; laptop installs start when `images/laptop.toml` exists (M3).

**Why now:** the settings file is the one way to describe a machine for the installer, the settings app, the shell, servers and fleets; building it before the shell means every later shell feature is a field in an existing file.

**Depends on:** M1.

Finished steps of this milestone: [ROADMAP-DONE.md](ROADMAP-DONE.md#m2-phase-1-now-one-file-describes-and-installs-a-machine).

**Parts after M2:** unchanged, plus two data formats (image definition, settings file), both TOML with a format number. **Deliberately not added:** cloud-init or tiny-cloud, Ansible-style scripts, polkit, an ISO, a separate installer, a migration registry before a format has changed.

**Principles check:** Reliable (fresh installs tested like updates, checkers refuse what they do not know while boot readers keep it and say so, ADR-008); Simple (one data file for the machine and its shell, four commands, the installer is a command); Scalable comes free from the same file later.

## M3 (phase 1, now): Release train, kept small

**Why now:** Alimardon needs a URL and a laptop image to try, budgets must exist before the desktop image grows, and the compatibility promise (ADR-005) needs old releases kept from the first one.

**Depends on:** M1, M2.

## M4 (next): The compositor

**Goal:** the desktop image boots in QEMU with a virtual GPU into our compositor: windows float with compositor-drawn title bars (close and maximize; minimize joins with M5.2's window list), one key or one line in `settings.toml` switches a workspace to dynamic tiling with the title bars kept, two outputs and fractional scaling work, X11 apps run with the same title bars, a broken compositor update falls back, and CI uploads a screenshot. Alimardon boots the preview on a laptop and moves windows.

**Why now:** the largest and riskiest part; its CI harness (virtual GPU, screenshots, frame budget) is what every shell step is proven with, so it is built first and alone.

**Depends on:** M3.

Finished steps of this milestone: [ROADMAP-DONE.md](ROADMAP-DONE.md#m4-next-the-compositor).

**Parts after M4:** plus the compositor (one process) and one data format, feature files (M4.0), which also takes the place of the add-on format M7.2 would have added; reused greetd, seatd, eudev, Mesa, XWayland, foot. **Deliberately not added:** a window-manager plugin or extension API, a second renderer, a session manager script, an IPC daemon, a settings daemon, golden-image tests.

**Principles check:** Reliable (rollback covers the desktop, greetd respawns); Instant (damage tracking proven by `idle_frames = 0`, a frame budget measured against sway from the first PR); Simple (one file watched, one trait, one supervisor, a test client instead of goldens). Beautiful waits for tokens in M5.

  Done when: an add-on test enables and starts a service from a simple unit file and `systemctl status` shows it running.
- [ ] **7. A drift check without an agent.** Server and managed images run `edel settings diff` daily from crond and write what drifted to the system log and `/run/edel/drift`; nothing is sent anywhere.
  Done when: server-test changes a key by hand, and the next run reports exactly that key.
- [ ] **8. Edge images with smaller slots.** The slot size becomes a choice of the image definition (today every install takes 4 GiB slots, M3.3b), so a device with 4 to 8 GB of flash keeps room for its data; a disk-layout change recorded in `docs/FORMATS.md`.
  Done when: an edge test image installs with 1 GiB slots and passes ab-test.
- [ ] **9. Review ZFS for data disks.** Asked by Alimardon on 2026-10-08, after hearing OpenZFS called better: look again at OpenZFS when this milestone comes up, decide then, and build nothing before. The system disk stays as it is: two whole slots already give atomic updates and rollback (ADR-006), a snapshot-based root was rejected (ADR-007, option B), ZFS's license keeps it out of the kernel, so its module must be rebuilt for every kernel and a failed rebuild could stop a boot (Reliable), and its cache wants memory our budgets do not have (Efficient). What it could give is for people's data on servers and home NAS boxes: checksums against silent corruption, snapshots, compression, many disks as one, and copying a disk to another machine. The review is `docs/REVIEW-zfs.md`: what OpenZFS on Alpine and musl costs then (module rebuilds per kernel, memory, the license), what btrfs and plain ext4 with mdraid give for the same needs, and a verdict, for Alimardon to decide: nothing, or ZFS as an add-on (ADR-007, level 2) for data disks only, never the root.
  Done when: `docs/REVIEW-zfs.md` with its verdict is in `SUMMARY.md` and the docs site builds in Rust checks (`sh ci/site.sh build`).

**Parts after M11:** unchanged; audit, AppArmor, the firewall and the adapter are features or add-ons. **Deliberately not added:** an enterprise edition, an enterprise-only security tier, a management server or fleet agent, SELinux, a compliance daemon, certifications before there is a company.

**Principles check:** Reliable and Scalable drive it: a slot that verifies itself and health checks of the image's own choosing keep unattended machines safe. Simple holds, because everything here is a feature, an add-on or a CI check on the same base. Efficient: consumer images get only what protects them too (the verified root, TPM unlock). Traded off: a slower road to buyers who want a Red Hat style system.

## M12 (an idea, not scheduled): Glasses and pocket PCs

**Goal:** a pocket-sized PC runs the desktop image and shows it in display glasses worn instead of a monitor: the whole desktop with its apps, floating in front of the eyes, as Apple's Vision Pro shows a Mac's screen, with the full power of a PC rather than a phone's. Asked by Alimardon on 2026-10-07, after an announcement of Meta's glasses that work with a small device kept in a pocket (from Alimardon's words; the product's details are not checked here), as the newest and furthest idea, written down so it is not lost.

**Why an idea only:** it needs phones and small devices first (M9) and hardware Alimardon chooses; it starts only on their word, and each step below is planned in detail then.

**Depends on:** M9 (form factors, arm64, docking).

- [ ] **1. Glasses as a screen.** Most display glasses today plug into USB-C with DisplayPort and appear as an ordinary monitor, so the desktop already lights them (M4.6c); the step tries real glasses with Alimardon, finds the right scale, and adds a **Glasses** preset: larger text, the panel kept near the middle of the view, dark by default, as glasses' displays add light to what is behind them.
- [ ] **2. Screens fixed in space.** The compositor places the desktop on one or more virtual screens that stay still as the head turns, reading the glasses' motion sensor and drawing each frame for where the head is now; reused from Monado, the open OpenXR runtime, rather than written, if it measures well. It must keep Instant: a gate on the time from a head turn to the frame that shows it.
- [ ] **3. A pocket PC image.** A small fanless x86_64 or arm64 box, or a handheld, that Alimardon picks as the reference, with battery and heat budgets in `ci/budgets.toml`, and the phone docked (M9.9) as a second way in.
- [ ] **4. Glasses that link without a cable.** Only for glasses that speak an open protocol to a nearby device; checked when the step starts.

**Parts after M12:** unchanged if Monado is reused; step 2 is a module of the compositor behind its screens. **Deliberately not added:** a 3D desktop of our own, a store for spatial apps, any closed vendor runtime in the base.

**Principles check:** Scalable and Versatile drive it: one base from a container to a pocket PC, one more form factor through a preset. Simple holds: glasses are a screen first, so step 1 needs no new part. Instant gates step 2, and Reliable keeps every device on the same A/B updates. Traded off: it waits behind everything else, so it costs nothing now.

## M13 (later, after the stable OS): Devices as one, the deep parts

**Goal:** the two ideas of ADR-011 nobody has made work for everyday apps, measured before anything is promised.

**Depends on:** M8 (the stable OS) and M7.10.

- [ ] **1. Spike: apps that travel.** A running app frozen with its unsaved work on one device and resumed on another with CRIU, its window reconnected (ADR-011, section 17), tried on three apps.
  Done when: CI freezes a test client on one VM and resumes it on another, its window and its state (a counter it draws) intact, or the spike writes down why not.
- [ ] **2. Spike: all your devices as one computer.** Idle plugged-in devices helping with a big job (a build, a video export, a local AI model), only with consent and never on battery (section 18).
  Done when: CI runs one job split over two VMs and measures the time against one VM, with the result in the run summary.

**Principles check:** Reliable and Simple keep both as spikes until a measurement shows a gain people can see; the seams of ADR-011's section 19, kept now, are what let them come later without a rewrite.

## Risks and how we retire them

- **smithay API churn and musl builds.** Package and crate names are from memory; the first compositor PRs may spend days on dependencies. Pin a version, split the skeleton in two PRs, keep the winit backend for development, say "check in CI" everywhere, correct the notes afterwards.
- **llvmpipe is not a GPU.** CI proves correctness and catches regressions; frame times, VRR and scanout on real hardware come only from Alimardon's laptops through `edel report`. Keep the CI frame budget conservative.
- **The bootloader is outside the rollback.** A GRUB binary that does not start leaves no slot reachable. Every transition runs in CI against every kept release's ESP (M3.5); loader changes are rare and reviewed; `BOOTX64.EFI.prev` is the manual way out.
- **Nothing has run on real hardware yet.** Every PR so far was proven in a VM under software rendering, and the outside review of 2026-10-06 found that apps could not use the GPU, which CI could not see. M3.6 puts the desktop on a USB stick before publishing, M5.19 gives CI a check for the GPU path, and the reference laptop's `edel report` gates each milestone once Alimardon names it.
- **OpenRC early boot ordering.** Services that write `/var` before `edel-data` mounts, or read `/etc` before the overlay, fail quietly. Three separate PRs (M1 steps 2 to 4) isolate each failure; our own init script via `mkinitfs -i` is the fallback with a written reason.
- **Alpine package gaps** (greetd, pam-rundir, gtk4-layer-shell, portal-wlr, Bazaar, fcitx5, squeekboard, FEX). A missing package turns a one-PR step into a packaging step that creates `packages/` and `ci/packages.sh`.
- **No logind.** Some portals or NetworkManager paths may insist on it; then elogind and perhaps polkit enter with the paragraph principle 3 demands.
- **CI time.** Desktop image, Flatpak downloads, the upgrade matrix over kept releases and six test suites can pass runner limits. Caches (cargo, runtimes), split jobs, nightly-only suites for arm64, fleet and old runtimes.
- **Flathub reachability and runtime size.** Cache runtimes or build a local test repo on the runner; the default app set is pulled once at build time.
- **Signing key held by one person.** A lost key strands every machine; two public keys in every image from M1 and an offline backup before the first public release.
- **The `/etc` overlay keeps a machine's old copy of a file whose default changed.** Our own defaults move to `/usr`; `edel settings export` shows the diff.
- **Phones.** Duranium boots SDM845 phones from a GPT inside `userdata` through U-Boot's UEFI; whether GRUB's try counter works the same way is unproven (M9.7 tests it first), and devices without U-Boot's UEFI would need a second counter. Nothing here is provable without hardware.
- **State on `/data` is shared by both slots.** The `/etc` upper layer, `settings.toml`, developer mode and add-on choices survive a fallback, so the slot fallback cannot undo them; lenient boot readers (ADR-008), Reset and `unset`, and the safe start (M7.1) are the answer.
- **Accessibility weight.** Orca with a voice adds 26 packages and 85.8 MiB (measured 2026-10-13, M6.9), more than the desktop image's room under its budget, so it comes as an add-on (M7.2) until a lighter reader exists; AT-SPI stays in the base.
- **Scope.** Ten milestones and about 89 PRs is a year or more of unattended work; the plan is adjusted in place rather than followed blindly, and the log below says what changed.

## What is deliberately not in the plan

RAUC, ostree or systemd (a systemd adapter only as an add-on, M11.6); a shell extension API, or a scripting layer for the shell as Quickshell's (not now, Alimardon said on 2026-10-06, who may ask for one later; settings, presets and tokens are how the desktop is made one's own, and developer mode is the way to full control); a theme engine or third-party theme format (appearance is a table of tokens); an ISO or squashfs live system; cloud-init, tiny-cloud or cloud-config parsing; polkit, elogind or dconf unless a reused service forces them; delta updates; a package lock or a mirror of Alpine; apk at update time; a Secure Boot shim or Microsoft signing; a long-support channel before M11.5 (ADR-009 records ten years as its goal); an enterprise edition, an enterprise-only security tier, a fleet agent or SELinux (ADR-009); Waydroid and NVIDIA's proprietary driver (NVK is the path); a notification daemon, a dock process, a separate greeter, a session manager script or a settings daemon; a store, a portal backend process or a container tool of our own; a second renderer; a Nix-style store; a Mesa rebuild for newer CPUs or an erofs slot format until a measurement asks for it; a build farm, a mirror network or a website before M8; golden-image screenshot tests; a feature framework (dependencies, versions, hooks or alternatives between features), runtime-loaded code or a plugin API of any kind, feature flags in shipped images, a schema-generated Settings UI, per-domain verbs that change settings (settings change only through `edel settings set` and `reset`), telemetry, a stick writer of our own for Windows or macOS, a look-change notice before the first visible redesign after the first public release (ADR-008).

## Principles check

Reliable drives the whole order: the update path, data survival, the watchdog guard, rollback by hand, signing and the fresh-install test come before a single pixel, old releases are kept from the first preview so the compatibility promise has something to be tested against, and every later milestone keeps the A/B, boot, install and upgrade tests green. Instant gets its measurement in the first compositor PR (frame telemetry against a sway baseline, idle frames, a budget) and its mechanism in M5 (effect tiers), not at the end. Simple is kept by the fewest-parts accounting at every milestone, by one system file for the machine and its shell, one kernel, one supervisor per level, add-ons and developer mode sharing one overlay, apk staying in CI, and by taking the apk repo, the lock gate, the migration registry and arm64 out of phase 1. Efficient has budgets before the desktop image exists. Beautiful and Functional follow in M5 and M6 through one token set, a default app set and a basics table with CI checks per audience. Powerful, Scalable and Versatile come after the first desktop, in M7 to M9, as files, add-ons and presets. Traded off: Alimardon waits about 19 PRs for something to look at (they can pull M4 forward), the loader stays outside the rollback and is protected by tests instead, and monthly full-image updates cost bandwidth until a measurement justifies deltas.
