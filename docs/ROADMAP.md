# Roadmap

**Status:** Proposed
**Date:** 2026-10-02
**Deciders:** Alimardon (order and vetoes), Claude (execution and defaults)

The plan from phase 0 (a base that boots, updates and rolls back in CI) to a first public release and beyond. It follows the ranked [design principles](DESIGN-PRINCIPLES.md) and the decisions in ADR-002 to ADR-008. The guiding idea is **fewest parts**: one tool (`edel`, inside the image and in CI), one file format (TOML with a format number), one image pipeline (`edel image build`, also for the live USB, add-ons and fleet images), one update path (a whole slot, carrying the bootloader; add-ons ride the same path), one file that describes a machine (`system.toml`, which also holds the shell, output and update settings the compositor and shell-ui watch). Every milestone says which parts exist after it and which were deliberately not added.

## How this roadmap is used

- Work starts when Alimardon says go. Claude then works through it step by step while Alimardon is away: one branch and one PR per step, merged when CI is green, then the box is ticked here and the next step starts.
- Each step is a few hundred lines and ends with **Done when:** a check CI runs (cargo tests, a QEMU boot with a line on the serial console, a screenshot pixel check, a container run). Claude has no hardware; Alimardon's trials on their laptops are the only hardware feedback and arrive as comments and `edel report` files.
- When a step turns out wrong or too big, Claude changes the plan in place (splits, reorders, rewrites "Done when") and says so under "Changes to the plan" at the end, dated.
- Open questions are not waited on. Claude takes the default listed under "Decisions taken by default" and lists it there; Alimardon overrules by commenting in the project. They can reorder or veto anything.
- Things that always wait for Alimardon's own words: anything outside this repository (new repositories, accounts, services, repository settings such as branch protection), spending money (runners, storage, domains, devices), publishing to the public (a release, a pre-release, a website, a registry), deleting data, and changing the license.
- Package names, crate names and versions marked "check in CI" are from memory; the first CI run of that step verifies them and the step's notes are corrected afterwards.

## Where we are

Phase 0 is merged to main (2026-10-01):

- `edel image build DEF.toml` (Rust, `crates/edel`) builds a container image (tar.gz) and a VM disk from Alpine 3.24 packages with apk, overlay files and OpenRC services. Definitions are `images/container.toml` and `images/vm.toml`, format 1.
- The VM disk is GPT: an EFI system partition with GRUB, slot A and slot B. GRUB counts boot tries per slot in `grubenv` with RAUC's variable names and falls back to the other slot after three failed tries. The `edel-boot-ok` service runs `edel-update mark-good` once the system is up.
- `edel-update` (a busybox sh script in `images/files/ab`) has `status`, `install IMAGE` (writes the other slot, checks sha256, fresh UUID, flips the boot order) and `mark-good`.
- CI builds everything inside a privileged `alpine:3.24` container, runs the container image, boots the VM with QEMU and OVMF to the login prompt, and runs the A/B test (install an update, reboot into it, install a broken update, watch it fall back). It reports image sizes.
- Decided: license GPL-3.0-or-later; our own updater (`edel update`), RAUC is not packaged; the name is Edel OS.

Since then (2026-10-02), M1 replaced `edel-update` with `edel update` in Rust and added the data partition, the read-only root with `/etc`, `/home`, `/var` and `/root` on it, the watchdog guard, signed updates from a URL and the boot loader riding along; M2 added the system file, `edel install` and the A/B test on a freshly installed disk; M3 added versions, budgets, the laptop image, 4 GiB slots, `edel report` and the release scripts (publishing waits for the release keys); M4.0 made images out of feature files and M4.1 added the desktop image and the CI display harness. Known gap, kept on purpose: GRUB writes the try counter at every boot.

## M1 (phase 1, now): One update path, finished

**Goal:** a VM installs a signed, gzip-compressed update straight from a URL, keeps `/home`, `/var` and its own `/etc` changes across the update, comes back on the old slot when the new one hangs (not only when it crashes), can be rolled back by hand, and the bootloader rides along in the same update. Alimardon can run `edel update install https://.../release.toml` on a VM and watch `edel update status`.

**Why first:** Reliable is principle 1, and every later feature is installed, copied and rolled back through this path. Today an update would erase the user's data.

**Depends on:** nothing. **Steps, in the order Claude does them next:**

- [x] **1. `edel update` in Rust replaces the shell script; rollback by hand.** `crates/edel/src/update.rs` (status, install IMAGE, mark-good, rollback) and `grubenv.rs` (parse and write the 1024-byte block, shared with `boot.rs`); slot discovery from `/proc/self/mountinfo` and `/sys/dev/block`; sha256 via the `sha2` crate; e2fsck, tune2fs and blockdev via `Command`. `rollback` flips ORDER to the other slot and refuses when that slot is off. `edel image build` copies `target/release/edel` into the rootfs (it is already built inside `alpine:3.24` against the image's musl); `images/files/ab/usr/sbin/edel-update` is deleted; `edel-boot-ok` and the ab-test files call `edel update`.
  Done when: cargo tests cover the grubenv round trip, ORDER/OK/TRY transitions for install, mark-good and rollback, and refusal to write the running slot or roll back to an off slot, against a mocked sysfs tree in a tempdir; ab-test passes with the Rust updater and gains a step that rolls back by command and boots the old slot. Notes: keep RAUC's variable names; pure functions take the env text and partition numbers so they test without a disk. `ci/build.sh` sets `CARGO_HOME=/src/.cargo-home` and `CARGO_TARGET_DIR=/src/target` so `actions/cache` keyed on `Cargo.lock` has something to cache. No apk packaging yet: `packages/` and `ci/packages.sh` arrive with the first step that needs apk resolution (a patched Alpine package, or M7). A lock (a file under `/run/edel` holding the pid, replaced when that process is gone) refuses a second `edel update` while one runs; the ESP is mounted only while grubenv is written, never in fstab, as the script does.
- [x] **2. Partition 4, `edel-data`.** `boot.rs` Layout gains partition 4 (ext4, label `edel-data`, 64 MiB in the image) after slot B so the slots stay partitions 2 and 3; `[vm] data_mib`; OpenRC sysinit service `edel-data` (after devfs, before the boot runlevel) runs `edel boot mount-data`: on first boot grows partition 4 to the end of the disk (`growpart DISK 4` from `cloud-utils-growpart`, which is in the v3.24 index (checked 2026-10-02), then `resize2fs`; it handles the relocated GPT backup header and the in-use disk in one call), mounts `LABEL=edel-data` at `/data`, prints `edel-data: mounted /data`.
  Done when: cargo tests for Layout (four partitions, no overlap, disk size, every GPT name 24 characters or fewer: longer names broke fastboot on the OnePlus 6); boot-test greps `edel-data: mounted /data`; a boot-test variant on a copy of the image grown by 3 GiB (`truncate`) shows `df /data` above 2 GiB (ext4 keeps about 7 percent for itself, measured in CI). Notes: container image untouched; sysinit because bootmisc and syslog write to `/var` early. If growpart is unavailable: `sfdisk --relocate gpt-bak-std`, `echo ', +' | sfdisk --no-reread -N 4`, then `partx -u`.
- [x] **3. Persistent `/home` and `/var`.** `edel boot mount-data` creates `/data/home` and `/data/var` and bind-mounts them over `/home` and `/var`. On every boot, before the bind, it copies into `/data/var` any top-level entry (and any `/var/lib` and `/var/log` entry) that exists in the slot's `/var` but not on `/data`, keeping symlinks such as `/var/run -> /run`, so an update whose packages add directories under `/var` boots with them present. `mark-good` records a fallback it finds (a slot it switches off) in `/data/edel/last-fallback.toml` (from, to, date) for shell-ui to show in M5.
  Done when: ab-test step 1 writes `/home/ab-marker` and `/var/ab-marker`; step 2, running on slot B, asserts both exist and that `/var/lib/ci-new` (carried by the update image in `ci/ab-test/files/var/lib/ci-new/`) exists; step 3, after the fallback, asserts the markers again and that `last-fallback.toml` names the broken slot. Notes: Flatpak and containers land in `/var` later and inherit survival for free.
- [x] **4. Read-only root with `/etc` changes on `/data`.** fstab mounts `/` with `ro`; `edel boot mount-data` overlay-mounts `/etc` (lower = the slot's `/etc`, upper = `/data/etc/upper`, work = `/data/etc/work`); `/tmp` on tmpfs (Alpine does not do this by default); `overlay` added to the kernel `modules=`. Before OpenRC starts services, `edel boot mount-data` adds the system users and groups the slot has but the upper `passwd`, `group` and `shadow` lack, since a machine's own copies would hide users a later slot adds (Duranium repairs this every boot); hostname, machine-id and password backups never come from the slot.
  Done when: boot-test greps `/ ... ro` from `/proc/mounts` printed on serial and `touch /usr/x` fails with EROFS; ab-test step 2 asserts a hostname changed in step 1 and the ssh host key fingerprint survived the update, and that a system user only the update image adds (in `ci/ab-test/files`) is in `getent passwd` after step 1 created a normal user. Notes: the real work is hunting stray writes to `/` service by service. OpenRC reads `/etc/rc.conf` early; if the sysinit ordering proves fragile, the fallback is our own init script passed with `mkinitfs -i FILE` (a copy of Alpine's initramfs-init with the `/data`, `/etc` overlay and `/var` mounts before switch_root), which is its own PR with a cargo-tested generator and a boot-test, since mkinitfs has no hook mechanism. The upper directory is the list of what this machine changed, and `edel system export` lists it (AerynOS lesson 1).
- [x] **5. A hanging slot falls back too.** `edel boot guard` replaces the mark-good call in `edel-boot-ok`: an OpenRC service started first in sysinit (after devfs, before mdev and hwdrivers) with `command_background=yes` and a pidfile, so start() returns at once and the guard runs on in the background (a service that blocked until the default runlevel would wait for itself). It opens `/dev/watchdog`, pets it every second until every health file named by `EDEL_HEALTH` in `/usr/lib/os-release` exists (`default-runlevel` means `/run/edel/default-reached`, which `edel-boot-ok`, kept in the default runlevel with `depend() { after *; }`, touches; `compositor` later means `/run/edel/session/ready`) or `EDEL_HEALTH_TIMEOUT` (120 s) passes; healthy means mark-good, magic close and exit, so no daemon stays; timeout means stop petting, the hardware resets, GRUB counts the try. `/run/openrc/softlevel` is never consulted: OpenRC writes it at the start of a runlevel change, while services may still hang. `edel image build` writes the `EDEL_*` keys into os-release from `[image] health` and `health_timeout` in the definition (one standard file, no new format; the version joins it in M3). Kernel `modules=` adds `i6300esb` and `softdog`; `ci/vm.sh` adds `-device i6300esb -action watchdog=reset`; `panic=10` on the cmdline covers plain crashes.
  Done when: cargo tests show the health check accepts the sentinel files only, not softlevel; ab-test gains two cases: (hang) an update whose default runlevel has a service that blocks forever, so the sentinel never appears; (freeze) an update whose default runlevel disables panic reboot and runs `echo c > /proc/sysrq-trigger`. Both come back on the previous slot with the broken one at ok=0. Notes: the ab-test image sets `health_timeout = 30` (the i6300esb default period) so the six failed tries cost minutes, not a quarter hour; release images keep 120. The freeze case is what tests the hardware watchdog; softdog alone would catch the hang. Older QEMU spells it `-watchdog i6300esb -watchdog-action reset` (check in CI); check that linux-virt ships `i6300esb` as a module; laptops have iTCO, softdog is the fallback. Start the guard in sysinit when `/dev/watchdog` already exists there (the modules load from the initramfs), so a hang in sysinit or boot is caught too (check in CI). A kernel panic reboots through `panic=10`, and Alpine's initramfs panics instead of waiting at its recovery shell when `panic=` is set (checked 2026-10-02).
- [x] **6. Signed releases, two keys, no downgrades.** `release.toml` (format = 1: version, channel, date, `images[]` with name, file, sha256, size, min_size, loader_version) plus `release.toml.sig`; `edel release sign|verify` with ed25519 (`ed25519-dalek`; check the musl build in CI); two public keys baked at `/usr/share/edel/keys/` through `[release] public_keys` in the image definition; PR runs use a throwaway key; `edel update install` refuses a manifest that fails verification, an image whose sha256 differs, and a version not newer than the running slot unless `--allow-downgrade`. The manifest is the one file an old slot reads from the future, so its reader ignores fields it does not know (the signature still covers them) and refuses only a format it does not know; `docs/FORMATS.md` states the stepping-stone rule: a manifest format bump publishes the new format under a new file name and keeps `release.toml` pointing at a release whose `edel` reads both (ADR-008).
  Done when: cargo tests (sign then verify, tampered manifest, wrong key, downgrade, a signed manifest with an unknown extra field verifies and installs, one with `format = 2` is refused naming the format); ab-test refuses a manifest with one flipped byte (`refused: signature` on serial) and then installs the good one. Notes: one key scheme for images, add-ons and manifests. A machine two formats behind installs the stepping stone, then the newer release at its next check, with no extra command (AerynOS users rerun theirs by hand). The second key exists from the first install so a rotation never strands a machine; the real key moves to a GitHub secret in M3 and an offline backup is Alimardon's job.
- [x] **7. Update from a URL, compressed, any slot size.** `edel update install URL` and `edel update check` (`ureq` with rustls, `flate2` for gzip), streaming the `.ext4.gz` into the slot while hashing; `edel image build` shrinks the slot image with `resize2fs -M` before gzip and records `min_size`, and emits `.ext4.gz` and `.img.gz` next to the raw files; install refuses an image whose `min_size` exceeds the slot and runs `resize2fs` on the target partition after the write, so a small image fills any slot; `ci/ab-test.sh` serves `out/` with `python3 -m http.server` on the runner and the VM reaches it at 10.0.2.2.
  Done when: ab-test step 1 installs from `http://10.0.2.2:8000/release.toml` with no second disk, using an update built with a smaller `slot_mib` than the running disk, and the VM boots it with `df /` showing the full slot; sizes.sh shows compressed sizes. Notes: rustls on musl, prefer the ring provider (check in CI); `file://` paths stay for USB installs; no delta updates until a measurement says the base is too big.
- [x] **8. The bootloader rides along in the update.** `edel image build` places the GRUB EFI binary, `grub.cfg` and a `loader.toml` (version = hash of both) under `/usr/lib/edel/boot/` in the rootfs; `edel update mark-good`, only after the slot is confirmed, compares with the ESP's `loader.toml` and installs the new loader by write to `.new`, fsync, rename, keeping `BOOTX64.EFI.prev`. `grub.cfg` stays compatible with both slots.
  Done when: ab-test builds the update image with `--loader-tag ci` so its loader differs; after the slot boots and is confirmed the ESP's `loader.toml` shows the new version; cargo test for the rename sequence in a tempdir. Notes: the loader is the one piece outside the A/B rollback: firmware loads one `BOOTX64.EFI`, and if it does not start, no slot is reachable and `.prev` only helps a person with a USB stick. The protection is that every loader transition is exercised in CI (M3.5 boots the old preview's ESP through the swap and once more) and that loader changes stay rare and reviewed; swap after confirmation, never at install time; the env block is never replaced; UEFI only. Call `syncfs` after the write and after the rename: a rename on FAT is not guaranteed atomic (AerynOS's blsforme works around vfat corruption).
- [x] **9. Flatpak on the musl base, checked early (standalone spike).** A CI-only definition `ci/flatpak/vm.toml` (vm plus flatpak, bubblewrap, dbus); `ci/flatpak-test.sh` adds Flathub as user `ci` (`flatpak --user`, the default for every later app install, so the data lives in `/home` and no polkit is needed), installs `org.freedesktop.Platform` (current branch, check), runs `flatpak run --command=sh org.freedesktop.Platform -c 'echo hello from glibc'`, and installs the oldest runtime Flathub still serves; `docs/SPIKE-flatpak.md` records the verdict, download sizes, whether unprivileged user namespaces work with Alpine's kernel config, and what `apk info -R flatpak` says about polkit arriving anyway.
  Done when: serial shows `hello from glibc` for the newest runtime, and the oldest runtime's result is recorded in `docs/SPIKE-flatpak.md`. Notes: no GUI and no compositor needed, so it runs now and retires the ADR-003 and ADR-005 risk for a few CI minutes.

**Parts after M1:** Linux kernel, Alpine base (busybox, OpenRC, apk), GRUB, `edel`. **Deliberately not added:** RAUC, ostree, systemd, a watchdog daemon, a separate update agent, an apk repository of our own, delta or zstd updates, LUKS, an initramfs change.

**Principles check:** Reliable drove the data partition, the guard, signing, rollback by hand and the loader swap after confirmation; Simple kept one tool, one partition layout and one standard file for image facts; Efficient won gzip and the shrunken image but lost the per-boot grubenv write to Reliable.

## M2 (phase 1, now): One file describes and installs a machine

**Goal:** `edel system export` on one VM and `edel system apply` on another give the same users, hostname and ssh keys; a blank disk becomes an Edel machine from a system file; CI tests a fresh install, then an update and a rollback on the installed disk, as principle 1 requires. All on a VM; laptop installs start when `images/laptop.toml` exists (M3).

**Why now:** the system file is the one way to describe a machine for the installer, the settings app, the shell, servers and fleets; building it before the shell means every later shell feature is a field in an existing file.

**Depends on:** M1.

- [x] **1. System file format v1.** `crates/edel/src/system.rs`: `format = 1`, `[system]` channel/version/variant/developer/profiles, `[users.NAME]` admin/ssh_keys/shell, `[network]` hostname, `[locale]` language/keyboard/timezone, `[shell]` preset/tiling/title_bars/form_factor, `[outputs.NAME]` position/scale/mode/enabled/transform, `[appearance]` wallpaper/color_scheme/accent/font/font_size/cursor_size/icon_size/motion, `[shortcuts]` action = keys, `[defaults]` browser/files/editor/terminal/mail, `[startup]` apps, `[power]` lid/idle/power_button/on_battery, `[services]` name = true or false, `[updates]` auto/window, `[apps]` flatpak, `[addons]` add (the three customization levels of ADR-007: everything here is level 1); serde without `deny_unknown_fields`, in a library target `edel::system` inside `crates/edel` whose network and signing dependencies sit behind the binary's default `cli` feature, so the compositor (M4.5), shell-ui (M5.1) and Settings (M5.6) parse with the same code and the same defaults table; unknown keys are collected with `serde_ignored` (check in CI) and enum-valued keys are parsed leniently (an unknown value or a wrong type falls back to the default and is reported, through a `#[serde(other)]` variant or a string mapped after parsing); `edel system check FILE` refuses an unknown key, value or format, naming the key and listing the allowed values, while the boot reader applies the rest and reports it; a cargo test fails when the structs lack a key listed in the committed, append-only `crates/edel/tests/keys.txt`, and CI fails a PR that deletes a line of it without bumping the format (ADR-008); `docs/system-file.md`. Keys that later milestones fill in are parsed now; check and set refuse them with "not supported yet", while the boot apply skips them and reports them, so adding them is not a format bump. Every loader `edel` owns checks `format`; checkers refuse an unknown format with a clear message, while the boot reader that meets a newer `system.toml` reads `system.toml.v<N>` beside it for its own N (left by `edel migrate` at a bump) or applies nothing and says so; a key is never removed or renamed within a format (a dropped key stays parsed and is reported as no longer used; an unavoidable rename reads both names); a value naming a preset, profile, add-on or feature this release lacks falls back to the default and is reported, never failing boot; `docs/FORMATS.md` states these rules. ADR-006's example is renamed from `[extensions]` to `[addons]` in the same PR.
  Done when: cargo tests parse the ADR-006 example; `edel system check` rejects `appearance.acent` naming the key, rejects `appearance.color_scheme = "sepia"` listing light, dark and auto, and rejects format 2, while the boot read of the same file applies every other key, uses the default scheme and reports both; a `system.toml.v1` beside a format-2 file is used, and with none nothing is applied; a key removed from the structs fails against `keys.txt`; everything round-trips through `toml::to_string`. Notes: `edel migrate` arrives with the first real format bump, when there is a real old file to test on (AerynOS lesson 2); a registry before that is machinery no principle asks for.
- [x] **2. `edel system apply`, at boot and on demand.** Applies hostname, users (busybox adduser; admin means the `admin` group; users without a password get `*` in `/etc/shadow`, never adduser's `!`, which OpenSSH treats as a locked account), `~/.ssh/authorized_keys` and the developer flag; OpenRC boot service `edel-system` with `depend() { before hostname; need localmount; }` applies the offline sections of `/data/edel/system.toml`, seeded on first boot in this order: a volume labelled `EDEL-SEED` holding `system.toml`, `/EFI/edel/system.toml` on the ESP, `/usr/share/edel/system.toml`; idempotent. Sections that need the network (`[apps]`) are applied only when a user or Settings calls apply, in the background.
  Done when: `ci/system-test.sh` builds a VM with a seed file creating user `ci` with a CI-generated ssh key, boots with `hostfwd=tcp::2222-:22`, `hostname` on serial equals the seed's value on the first boot, and `ssh -p 2222 ci@localhost edel system export` succeeds; cargo test for the shadow line. Notes: apply never deletes users it did not create; password hashes live in the `/etc` overlay on `/data`, never in the file.
- [x] **3. `edel system export`, `diff`, `set` and `unset`.** Export writes `system.toml` plus the list of files in `/data/etc/upper`; diff is a dry run of apply and exits 0 when there is nothing to do, listing not-yet-installed apps as pending rather than drift; `edel system set KEY=VALUE` edits one key in place with `toml_edit`, so comments, order and keys this slot does not know survive byte for byte (the compositor and Settings use it from M4 on); `set` refuses an unknown key or value it is asked to write, keeps and reports unknown keys already in the file, and on a newer-format file changes `system.toml.v<N>` and says the change applies to this release only; `unset KEY` removes a key, and apply enforces the release default for every absent key it owns, taken from the defaults table in `edel::system` filled from the slot (for a file in the `/etc` overlay such as `/etc/hostname`, by removing the upper copy); no writer ever writes a default; diff also lists ignored keys, unknown values and unknown names (ADR-008).
  Done when: system-test: apply, export, diff is empty; `edel system set network.hostname=other` and diff shows exactly that one change; after `unset network.hostname` and apply, `hostname` prints the image's hostname; a line `future.key = 1` and a hand-written comment above `[users.ci]` survive the set and the unset byte for byte.
- [x] **4. `edel install DISK --system FILE`.** Partitions the target with `boot.rs` Layout, copies the running slot's partition to slot A with a fresh UUID, writes the ESP from `/usr/lib/edel/boot` and an initial grubenv, creates `edel-data` and puts the system file in it; refuses the disk it runs from. `sfdisk`, `dosfstools` and `mtools` join `images/vm.toml` (today they live only on the build host). Install builds one plan in `edel::system` (the disk's model and size, and its partitions with labels and filesystems, such as `Windows (NTFS, 420 GB)`) and uses it three ways: `--dry-run` prints it and changes nothing, a terminal run prints it and asks the person to type the disk's name, and a run with neither a terminal nor `--yes` prints it and exits 3 (ADR-008).
  Done when: `ci/install-test.sh` boots the VM image with a blank second virtio disk, a test service (`command_background=yes` and a pidfile like the guard, waiting until `edel update status` shows the running slot confirmed, so the guard never waits on it) first runs `edel install /dev/vdb --system /usr/share/edel/ci/install.toml` without `--yes` (serial shows the plan and exit code 3, vdb's sha256 is unchanged) and then with `--yes`, QEMU then boots vdb alone to the file's hostname at the login prompt with slot A confirmed and ssh host keys that differ from the live image's; a cargo test asserts the install plan uses only tools listed in the image definition. Notes: no ISO; the disk image written to a USB stick is the live medium and the installer; copying the running slot avoids carrying a payload inside a slot.
- [x] **5. Fresh install plus update plus rollback, required.** `ci.yml` runs install-test and then ab-test against the installed disk; docs say the job is required for merging (branch protection is a repository setting Alimardon turns on).
  Done when: a test branch that breaks a first-boot service fails the job. Notes: AerynOS lesson 3, enforced rather than remembered.

**Parts after M2:** unchanged, plus two data formats (image definition, system file), both TOML with a format number. **Deliberately not added:** cloud-init or tiny-cloud, Ansible-style scripts, polkit, an ISO, a separate installer, a migration registry before a format has changed.

**Principles check:** Reliable (fresh installs tested like updates, checkers refuse what they do not know while boot readers keep it and say so, ADR-008); Simple (one data file for the machine and its shell, four commands, the installer is a command); Scalable comes free from the same file later.

## M3 (phase 1, now): Release train, kept small

**Goal:** every merge to main produces signed images Alimardon can download and try, on a VM or by writing `edel-laptop` to a USB stick; a tag produces a draft release that is kept forever; images carry a version, a platform level and the list of packages inside them; CI fails on size, memory and boot-time budgets; every kept release is upgraded to the PR's build in CI.

**Why now:** Alimardon needs a URL and a laptop image to try, budgets must exist before the desktop image grows, and the compatibility promise (ADR-005) needs old releases kept from the first one.

**Depends on:** M1, M2.

**Principles check:** Reliable (signed delivery, the upgrade test from every kept release, the loader transition tested); Efficient (budgets before the desktop image exists); Simple kept GitHub as the only host, one kernel and a record instead of a lock gate.

## Risks and how we retire them

- **smithay API churn and musl builds.** Package and crate names are from memory; the first compositor PRs may spend days on dependencies. Pin a version, split the skeleton in two PRs, keep the winit backend for development, say "check in CI" everywhere, correct the notes afterwards.
- **llvmpipe is not a GPU.** CI proves correctness and catches regressions; frame times, VRR and scanout on real hardware come only from Alimardon's laptops through `edel report`. Keep the CI frame budget conservative.
- **The bootloader is outside the rollback.** A GRUB binary that does not start leaves no slot reachable. Every transition runs in CI against every kept release's ESP (M3.5); loader changes are rare and reviewed; `BOOTX64.EFI.prev` is the manual way out.
- **OpenRC early boot ordering.** Services that write `/var` before `edel-data` mounts, or read `/etc` before the overlay, fail quietly. Three separate PRs (M1 steps 2 to 4) isolate each failure; our own init script via `mkinitfs -i` is the fallback with a written reason.
- **Alpine package gaps** (greetd, pam-rundir, gtk4-layer-shell, portal-wlr, Bazaar, fcitx5, squeekboard, FEX). A missing package turns a one-PR step into a packaging step that creates `packages/` and `ci/packages.sh`.
- **No logind.** Some portals or NetworkManager paths may insist on it; then elogind and perhaps polkit enter with the paragraph principle 3 demands.
- **CI time.** Desktop image, Flatpak downloads, the upgrade matrix over kept releases and six test suites can pass runner limits. Caches (cargo, runtimes), split jobs, nightly-only suites for arm64, fleet and old runtimes.
- **Flathub reachability and runtime size.** Cache runtimes or build a local test repo on the runner; the default app set is pulled once at build time.
- **Signing key held by one person.** A lost key strands every machine; two public keys in every image from M1 and an offline backup before the first public release.
- **The `/etc` overlay keeps a machine's old copy of a file whose default changed.** Our own defaults move to `/usr`; `edel system export` shows the diff.
- **Phones.** Duranium boots SDM845 phones from a GPT inside `userdata` through U-Boot's UEFI; whether GRUB's try counter works the same way is unproven (M9.7 tests it first), and devices without U-Boot's UEFI would need a second counter. Nothing here is provable without hardware.
- **State on `/data` is shared by both slots.** The `/etc` upper layer, `system.toml`, developer mode and add-on choices survive a fallback, so the slot fallback cannot undo them; lenient boot readers (ADR-008), Reset and `unset`, and the safe start (M7.1) are the answer.
- **Accessibility weight.** Orca and its dependencies may break the Efficient budget; a documented exception until a lighter reader exists.
- **Scope.** Ten milestones and about 89 PRs is a year or more of unattended work; the plan is adjusted in place rather than followed blindly, and the log below says what changed.

## What is deliberately not in the plan

RAUC, ostree or systemd; a shell extension API; a theme engine or third-party theme format (appearance is a table of tokens); an ISO or squashfs live system; cloud-init, tiny-cloud or cloud-config parsing; polkit, elogind or dconf unless a reused service forces them; delta updates; a package lock or a mirror of Alpine; apk at update time; a Secure Boot shim or Microsoft signing; an LTS channel before users ask; Waydroid and NVIDIA's proprietary driver (NVK is the path); a notification daemon, a dock process, a separate greeter, a session manager script or a settings daemon; a store, a portal backend process or a container tool of our own; a second renderer; a Nix-style store; a Mesa rebuild for newer CPUs or an erofs slot format until a measurement asks for it; a build farm, a mirror network or a website before M8; golden-image screenshot tests; a feature framework (dependencies, versions, hooks or alternatives between features), runtime-loaded code or a plugin API of any kind, feature flags in shipped images, a schema-generated Settings UI, per-domain verbs that change settings (settings change only through `edel system set` and `unset`), telemetry, a stick writer of our own for Windows or macOS, a look-change notice before the first visible redesign after the first public release (ADR-008).

## Principles check

Reliable drives the whole order: the update path, data survival, the watchdog guard, rollback by hand, signing and the fresh-install test come before a single pixel, old releases are kept from the first preview so the compatibility promise has something to be tested against, and every later milestone keeps the A/B, boot, install and upgrade tests green. Instant gets its measurement in the first compositor PR (frame telemetry against a sway baseline, idle frames, a budget) and its mechanism in M5 (effect tiers), not at the end. Simple is kept by the fewest-parts accounting at every milestone, by one system file for the machine and its shell, one kernel, one supervisor per level, add-ons and developer mode sharing one overlay, apk staying in CI, and by taking the apk repo, the lock gate, the migration registry and arm64 out of phase 1. Efficient has budgets before the desktop image exists. Beautiful and Functional follow in M5 and M6 through one token set, a default app set and a basics table with CI checks per audience. Powerful, Scalable and Versatile come after the first desktop, in M7 to M9, as files, add-ons and presets. Traded off: Alimardon waits about 19 PRs for something to look at (they can pull M4 forward), the loader stays outside the rollback and is protected by tests instead, and monthly full-image updates cost bandwidth until a measurement justifies deltas.
