# Features: how images are made

**Date:** 2026-10-02 (roadmap M4.0), amended 2026-10-03 (M4.1: the desktop's features; M4.2b: `programs` and the compositor)

Every Edel OS image is a list of features. A feature is one file, `features/NAME.toml`, and an optional directory, `features/NAME/`, copied over the root; an image definition (`images/*.toml`) names the features it is made of and holds only facts about the image. The rules are ADR-008's; this page is the maintainer's how-to. Adding, swapping or dropping a feature is one PR, and machines meet it as one A/B update that rolls back.

## A feature file

```toml
# features/ssh.toml; features/ssh/, if present, is copied over the root
format = 1
summary = "Log in from another computer with ssh"   # one line for people
why = "Servers and virtual machines are run from afar, and ssh is how; ..."
packages = ["openssh-server"]
modules = []        # kernel modules the initramfs loads first (modules=)
initramfs = []      # mkinitfs features
switchable = true   # may ship off (off = [...]); services.ssh later (M6.10)
screen = false     # needs a screen (M8.17): off on a machine with no graphics card
addon = false       # also built as a signed add-on (M7.2a)
features = []       # an add-on made of these features (M8.17c)
on = "desktop"      # an add-on built over this add-on (M8.17c)
health = []         # health checks it writes, which the boot guard waits for
programs = []       # our own programs it ships in /usr/bin (edel-compositor)

[services]
default = ["sshd"]  # also sysinit, boot, shutdown

[[keep]]            # what the image keeps of its packages' files (M5.30)
under = "lib/firmware"
files = ["i915/*", "intel/iwlwifi/*"]   # patterns below `under`; the rest goes
newest = ["intel/iwlwifi/*"]            # of these, the newest version only
newest_by = "iwlwifi"                   # no newer than this module asks for
```

| Field | Rule |
|---|---|
| `format` | 1 |
| `summary` | Required, one line |
| `why` | Required when the feature adds a package or a service: the written reason of principle 3, now a build check |
| `packages`, `services` | Alpine package names; OpenRC services by runlevel, each in one runlevel. A service's `/etc/init.d/NAME` comes from a package or a feature's directory |
| `modules`, `initramfs` | Only a-z, 0-9, `_` and `-`. Images without a kernel ignore them |
| `programs` | Programs of this repository's workspace the feature ships in `/usr/bin`, such as `edel-compositor`; `edel image build` copies each from beside itself, where `cargo build --release --workspace` leaves it, so list the libraries it links in `packages`, which apk cannot see. A program needs a `why` |
| `flatpak`, `flatpak_dropped` | `flatpak`: the `apps` feature's default apps, baked into the image (M6.2), or an add-on's apps, which `edel settings apply` installs for each administrator while `addons.installed` names the add-on, never baked in, even where the add-on is built in (M7.9). `flatpak_dropped`: only in the `apps` feature |
| `[[keep]]` | What the image keeps under a folder of the root (M5.30, `edel::keep`): `under` (such as `lib/firmware`), `files`, patterns below it where `*` and `?` stay inside one folder, and optionally `newest` (some of `files`) with `newest_by`, a kernel module: of each family of versioned files (`iwlwifi-so-a0-gf-a0-89.ucode`), only the newest version no higher than the module declares stays, and a family it does not declare keeps every version. A link stays when it is listed and what it points at stays. Every other file under the folder is taken out before the initramfs is made. A pattern that matches nothing fails the build, and two features may not list the same folder. The laptop feature's list is the stick's firmware, by device |
| `features` | Only with `addon = true` (M8.17c): the features the add-on is made of, such as the desktop's 18. Such an add-on brings nothing of its own; each part keeps its own file and may bring packages, services, programs, health, `screen`, the default apps and plain `[[keep]]` lists, never kernel modules, mkinitfs features or keep-`newest`. A part is listed in no image's `features` and in one add-on only |
| `on` | Only with `addon = true` (M8.17c): the add-on this one is built over, listed before it in the image, which is built on the image alone. It is built from a copy of that add-on's root, lies above it over `/usr`, keeps its copy of the merged caches and the fonts' cache, and stays off on a machine without it (`add-on orca needs the desktop add-on`) |
| `screen` | `true` for a feature that needs a screen: `seat`, `login`, `compositor`, `power`, `bluetooth` and `firewall` (M8.17, M8.14). On a machine whose kernel shows no graphics card (`edel::services::has_screen`), `edel settings apply --boot` takes their default runlevel's services out (their boot services run everywhere and do nothing there), deciding once per boot (`places::SCREEN`), and the boot guard does not wait for the health checks of these features that no other feature lists (`EDEL_HEALTH_SCREEN`); a machine with a screen starts them as before. For a switchable one (`bluetooth`), a key the settings file sets wins. The other way round, an image's `headless` list (the one image's `ssh`) names switchable features on by default where there is no screen |
| `while_set` | A settings key that switches a switchable feature (M7.5): its services run only while the key is set to anything but `off` or `false`, and `services.NAME` still wins. `updates` follows `updates.automatic`, so crond runs only while someone chose automatic updates |
| `[alpine]` | `branch`, `mirror`, `repositories` and `image_digest`: only in the `base` feature, the one owner of the Alpine branch every image is built from and of CI's build container, which follows the branch and is pinned to the digest (M5.27, M3.9); its `[alpine.users]` and `[alpine.groups]` pin the id of every system account (100 to 999) the packages add, which the build moves each account to and fails without (`account_ids.rs`), so a newer slot's or an add-on's account never takes an id a machine gave another |
| `[[basics]]` | The basics checklist's rows this feature brings (M6.7, `ci/basics-test.sh`): `name`, at most 40 characters and unique in the feature; then either `test`, the desktop-test case that proves it (lowercase letters, digits and hyphens, such as `sound`), or `needs`, `"hardware"` or the roadmap step that brings it (`M` and digits, optionally `.` and digits with lowercase letters, such as `"M7.8"`). A row with both or neither is refused by `check`. The table in CI shows each row PASS, needs hardware or comes in its step |

A basic a person expects to work (Audio, Network, Battery) is a `[[basics]]` row of the feature that brings it, so the checklist in CI follows the features: a feature added adds its rows, a feature dropped drops them.

No dependencies, versions, scripts or alternatives between features: apk resolves packages. The one exception is an add-on's `on` (M8.17c), which names the add-on whose files it is built over. A package one image needs alone goes into a feature named after that image (`container`).

## An image definition (format 2)

```toml
format = 2
name = "edel"
variant = "vm"
arch = "x86_64"
hostname = "edel"
features = ["base", "machine", "udev", "ab-boot", "ssh", "kernel", "laptop", "completion", "graphics", "seat", "login", "fonts", "terminal", "compositor", "shell", "settings", "xwayland", "sound", "network", "bluetooth"]
off = ["ssh"]       # installed, its service off

[vm]
kernel = "lts"      # a listed feature must install linux-lts
slot_mib = 1536
cmdline = "console=tty0 console=ttyS0,115200"   # never modules=
```

`[vm] carry` (M8.17c) names add-ons of the image the disk holds on its data partition, in the version's folder, and names in os-release as `EDEL_ADDONS_DEFAULT`: a machine whose settings file sets no `addons.installed` of its own has them (`edel::addon_state::installed`), so the stick and a machine installed from it start the desktop, and a server leaves it out with `addons.installed = []`. A change to the list (`+=`, `-=`) starts from that default, and an update reads the new slot's.

Besides these, a definition has only `[image] health_timeout` and `[release] public_keys`. Format 1 (packages and services in the definition) is refused: every definition lives in this repository and was converted in M4.0.

## What `edel image build` does with them

- **Finds** features in `features/` beside the definition, if there is one (CI's test features under `ci/`), and in the repository's, the `features/` of the nearest directory above that also holds `images/`. It checks every feature file there strictly, so an unknown field, a `NAME/` without `NAME.toml` or any other file in a features directory stops the build even when no image lists it.
- **Merges** the listed features in order: packages, services, modules, health files, programs and mkinitfs features as sets, so several features may list `dbus`; modules keep the order they are first named in (`modules=` loads them in that order), and the mkinitfs features are sorted.
- **Refuses** a health name that nothing writes: `default-runlevel` and `compositor` are edel's own, and any other name (a-z, 0-9 and '-', such as a server's `network`) is a feature's own check, its file `$health_dir/NAME` (`/run/edel/health/NAME`, from `places.sh`), which a file one of the image's features ships must write, as its service does once the check passes (M1.11). A check finishes well inside `health_timeout`, or every update falls back.
- **Refuses** an unknown feature, one listed twice, a missing `why`, one service in two runlevels, a file path shipped by two features, an `off` entry that is not listed or not switchable, an image with variant `vm` without health, modules, mkinitfs features or its kernel package, and a container image with health.
- **Keeps** under each `[[keep]]` folder only what the list keeps, right after the packages are installed and before the initramfs is made, and prints `kept N files under /FOLDER (X MiB), took out M (Y MiB)`; a pattern that matches nothing stops the build.
- **Ships** each listed feature's file as `/usr/share/edel/features/NAME.toml`, writes the union of health as `EDEL_HEALTH` and the `off` list as `EDEL_SERVICES_OFF` in os-release, installs the packages of every listed feature, copies their programs to `/usr/bin`, and enables the services of those not in `off`.

On a machine, feature files are read leniently: `edel report` lists the features in `/usr/share/edel/features/` and notes any field it skipped (`edel::features::read`), so an older release can read a newer feature file. `edel image check` and the build use the strict `edel::features::check`.

## Add-ons (M7.2a)

An add-on is a feature with `addon = true`, built not into an image but beside it, from the image's own root, so it fits that image's exact packages. An image definition names the add-ons built from it, `addons = ["fonts-cjk", "orca"]`; a feature an image lists in `features` is built in there and cannot also be its add-on.

- **Build.** After the image is packed, `edel image build` copies its root, adds the add-on's packages with apk from the same package index, copies `features/NAME/` and the feature file, and keeps what changed. New files under `/etc/init.d/` move to `/usr/lib/edel/init.d/`, the rest of `/etc` to `/usr/lib/edel/etc/NAME/` and `/var` to `/usr/lib/edel/var/NAME/`, and programs and libraries Alpine puts in `/bin`, `/sbin` and `/lib` move under `/usr`; the new lines the packages added to `/etc/passwd`, `group` and `shadow` go to `/usr/lib/edel/accounts/NAME/`. Anything else outside `/usr` (the kernel's modules and firmware too), a file of the image taken out, or a file of the image changed (a link by its target) stops the build, naming the path. A busybox link a package replaces with its own program (`bc` for printing) is no change: the add-on keeps busybox's. Of the caches apk's triggers rewrite, the ones apps check against their folder's time and go without (the icon caches) or rebuild (fontconfig's) and apk's own files are left out, so the slot's are used and apps read an add-on's icons and fonts a little slower; the ones nothing reads the sources of (compiled GSettings schemas, the GIO, gdk-pixbuf and GTK module caches, the MIME and desktop databases) are kept, as the add-on's copy holds the image's entries and its own, and the overlay shows it over the slot's; two add-ons that change the same one are refused as two shipping one file unalike, and the maintainer puts the packages that change it into one add-on. (Seam: should two add-ons one day need different schemas, the handful of caches can be generated once per mounted set at boot, with the generators the image already has, into a layer of their own above the add-ons; not built now, as no add-on needs it and a boot step costs time and failure modes.) The result is `IMAGE.NAME.ext4.gz` and its feature file `IMAGE.NAME.toml`, in the build's output.
- **One path, one owner.** An add-on keeps only files its image lacks, so it never ships one of the image's; the build stops when two add-ons of one image ship different files at one path, or add one user, group or id in different lines. Each add-on is built with the account lines of those built before it in its copy of the root while its packages go in, so apk gives its new users and groups ids none of them has (M8.17c). Two add-ons that need one package each carry the same copy of its files, which is no clash: the overlay shows one, and either serves.
- **Made of features, built over another (M8.17c).** An add-on with `features` installs its parts' packages, copies their files and programs and ships every part's feature file, so a machine with it reads them as built-in ones (the screen rule, the guard's health, the basics, the default apps); an add-on with `on` starts from its base add-on's root instead of the image's. Both bake the fonts' cache and keep it. The build checks each add-on against the platform level with the image's features and its parts. A VM image builds its add-ons right after its slot, so its disk can carry them.
- **Release.** `edel release make --addon FILE` lists each add-on in `release.toml` with its image, the base version it was built on (the release's), its summary, its file, sha256 and size, all under the release's signature.
- **Update.** `edel update` writes and checks the slot, then fetches the add-ons `addons.installed` names for this image into `/data/addons/VERSION/NAME.ext4` with the same checks; a failed fetch leaves the new slot off and the running system untouched. A name the new list lacks is skipped with `add-on NAME is not in VERSION`, and one the new slot builds in with `add-on NAME is built into VERSION`, so a dropped add-on never strands a machine. Only the folders of the two slots' versions are kept, so add-ons roll back with their slot.
- **Boot.** `edel boot mount-data` mounts each add-on of the running version that `addons.installed` names read-only under `/run/edel/addons/NAME` and lays them over `/usr` in one overlay, in the order `addons.installed` lists them, an add-on built `on` another above it, and one whose base is not there left off; an add-on that does not mount is said and skipped. The boot guard waits for the health the mounted add-ons' features write, from their feature files under `/run/edel/addons`, and apply enables the services of an add-on's parts. The add-ons' accounts are merged into `/etc` as the slot's are, and their `/var` entries are copied into `/data/var` wherever the machine lacks them. When a mounted add-on brings a service, `edel boot mount-data` has OpenRC read the services again once `/etc` has its layer, as OpenRC read them before it and would otherwise never start the add-on's service. When a mounted add-on brings rules for udev under `/usr/lib/udev/rules.d` (printing's scanners, gaming's controllers) and udev runs, `edel boot mount-data` has udev read its rules again and announce every device once more as a change, as udev read them, and announced the devices present at boot, before the add-ons were over `/usr` (M7.6b).
- **Apply.** `edel settings apply` links each mounted add-on's `/etc` entries and init scripts into `/etc` and its services into their runlevels (OpenRC reads a linked script's `conf.d` beside the script, so the slot links `/usr/lib/edel/conf.d` to `/etc/conf.d`, M8.17c), and takes out every link of ours whose add-on is gone, so a rollback leaves no dangling service. When a service's script or `conf.d` file comes or goes, apply has OpenRC read the services again before the service joins its runlevel, as OpenRC remakes its cache of them on its own only when `/etc/init.d` is newer than the cache to the second, which a boot can miss.
- **List.** `edel addon list` prints the add-ons of this image in the channel's list, with their summaries and whether each is installed or built in, and the line that installs one: `edel settings set addons.installed+=NAME`.
- **Apps.** An add-on may list Flatpak apps (`flatpak`, M7.9; `ai-agents` does). `edel settings apply` installs them for each administrator, with `apps.installed`'s, while `addons.installed` names the add-on (read through `edel::profiles::applied`), from the slot's copy of the offered add-ons' files, so they come with no restart; the add-on's own image then holds only its feature file. Dropping the add-on installs nothing more and uninstalls nothing, as with `apps.installed`.
- **Hardware packs (M7.11, ADR-012).** An add-on whose feature file has `hardware` is a hardware pack: `hardware` lists the modalias patterns it serves (`*` any run of characters, `?` one, as `/sys/bus/*/devices/*/modalias` shows them, such as `pci:v000010DEd*bc03sc*`). Only an add-on may have it, and each pattern needs a `:` and no `/` or white space. A pack is built, fetched, mounted and chosen like any add-on. Its files come in through the add-on's overlay on `/usr`, so the kernel finds its firmware at `/usr/lib/firmware`. At each start, after the add-ons are mounted, a device a mounted pack serves that has no driver is started again; `edel status`, Settings' Add-ons page and one notification name the packs that serve this computer and are not chosen (`/run/edel/hardware-packs`, written at each start).

## Worked examples

Each is one PR.

| Change | Files the PR touches | What machines see |
|---|---|---|
| Add a feature, say printing | `features/printing.toml` with `why`, `switchable = true` and later `addon = true`; `features/printing/` if it ships files; one line in each image's `features` | The packages and services arrive with the next update; with `addon = true`, only for those who pick it (M7.2a) |
| Replace a daemon (NetworkManager for busybox networking) | The feature's `packages` and `[services]` and its directory | Settings keys keep their names; the daemon's own state is converted in the PR or named in the release notes |
| Ship a feature off | The image's `off = ["NAME"]`; the feature must be `switchable` | Its packages are there, its services do not start; `EDEL_SERVICES_OFF` names it |
| Move a package between features | Both feature files | Nothing, if every image lists both |
| Drop a feature | Delete `features/NAME.toml` and `features/NAME/`, and its line in each definition; a leftover directory fails the build | Its packages and services are gone after the update; a rollback brings them back |
| A test-only feature | `ci/<test>/features/NAME.toml` beside a CI-only definition | Nothing: release images never list it |

A cargo test (`def::tests`) fails when a change makes an image install or enable something its features do not explain: it rebuilds main's format-1 definitions from `crates/edel/tests/format1/` and compares, and dropping `ssh` from the VM must drop exactly `sshd` and `openssh-server`.

## Principles check

- **Reliable:** strict checks at build time refuse a broken or ambiguous feature before any image exists; lenient reading on a machine never stops an older release; the merge was proven against the previous definitions.
- **Simple:** one file per feature, one way to put a package or service into an image, no dependencies or scripts between features, and the old `files` lists and the `boot::MODULES` and `INITRAMFS_FEATURES` constants are gone.
- **Efficient:** nothing runs at boot for this; each image carries a few small TOML files.
- **Scalable:** the desktop, phone and later images are lists of the same features.
- **Traded off:** two lookup places (beside a CI definition and the repository's) instead of one, so test features stay under `ci/`; a feature per piece (15 since M4.1) where one list per image was shorter to read.
