## M1 (phase 1, now): One update path, finished

- [x] **1. `edel update` in Rust replaces the shell script; rollback by hand.** `crates/edel/src/update.rs` (status, install IMAGE, mark-good, rollback) and `grubenv.rs` (parse and write the 1024-byte block, shared with `boot.rs`); slot discovery from `/proc/self/mountinfo` and `/sys/dev/block`; sha256 via the `sha2` crate; e2fsck, tune2fs and blockdev via `Command`. `rollback` flips ORDER to the other slot and refuses when that slot is off. `edel image build` copies `target/release/edel` into the rootfs (it is already built inside `alpine:3.24` against the image's musl); `images/files/ab/usr/sbin/edel-update` is deleted; `edel-boot-ok` and the ab-test files call `edel update`.
  Done when: cargo tests cover the grubenv round trip, ORDER/OK/TRY transitions for install, mark-good and rollback, and refusal to write the running slot or roll back to an off slot, against a mocked sysfs tree in a tempdir; ab-test passes with the Rust updater and gains a step that rolls back by command and boots the old slot. Notes: keep RAUC's variable names; pure functions take the env text and partition numbers so they test without a disk. `ci/build.sh` sets `CARGO_HOME=/src/.cargo-home` and `CARGO_TARGET_DIR=/src/target` so `actions/cache` keyed on `Cargo.lock` has something to cache. No apk packaging yet: `packages/` and `ci/packages.sh` arrive with the first step that needs apk resolution (a patched Alpine package, or M7). A lock (a file under `/run/edel` holding the pid, replaced when that process is gone) refuses a second `edel update` while one runs; the ESP is mounted only while grubenv is written, never in fstab, as the script does.
- [x] **2. Partition 4, `edel-data`.** `boot.rs` Layout gains partition 4 (ext4, label `edel-data`, 64 MiB in the image) after slot B so the slots stay partitions 2 and 3; `[vm] data_mib`; OpenRC sysinit service `edel-data` (after devfs, before the boot runlevel) runs `edel boot mount-data`: on first boot grows partition 4 to the end of the disk (`growpart DISK 4` from `cloud-utils-growpart`, which is in the v3.24 index (checked 2026-10-02), then `resize2fs`; it handles the relocated GPT backup header and the in-use disk in one call), mounts `LABEL=edel-data` at `/data`, prints `edel-data: mounted /data`.
  Done when: cargo tests for Layout (four partitions, no overlap, disk size, every GPT name 24 characters or fewer: longer names broke fastboot on the OnePlus 6); boot-test greps `edel-data: mounted /data`; a boot-test variant on a copy of the image grown by 3 GiB (`truncate`) shows `df /data` above 2 GiB (ext4 keeps about 7 percent for itself, measured in CI). Notes: container image untouched; sysinit because bootmisc and syslog write to `/var` early. If growpart is unavailable: `sfdisk --relocate gpt-bak-std`, `echo ', +' | sfdisk --no-reread -N 4`, then `partx -u`.
- [x] **3. Persistent `/home` and `/var`.** `edel boot mount-data` creates `/data/home` and `/data/var` and bind-mounts them over `/home` and `/var`. On every boot, before the bind, it copies into `/data/var` any top-level entry (and any `/var/lib` and `/var/log` entry) that exists in the slot's `/var` but not on `/data`, keeping symlinks such as `/var/run -> /run`, so an update whose packages add directories under `/var` boots with them present. `mark-good` records a fallback it finds (a slot it switches off) in `/data/edel/last-fallback.toml` (from, to, date) for shell-ui to show in M5.
  Done when: ab-test step 1 writes `/home/ab-marker` and `/var/ab-marker`; step 2, running on slot B, asserts both exist and that `/var/lib/ci-new` (carried by the update image in `ci/ab-test/files/var/lib/ci-new/`) exists; step 3, after the fallback, asserts the markers again and that `last-fallback.toml` names the broken slot. Notes: Flatpak and containers land in `/var` later and inherit survival for free.
- [x] **4. Read-only root with `/etc` changes on `/data`.** fstab mounts `/` with `ro`; `edel boot mount-data` overlay-mounts `/etc` (lower = the slot's `/etc`, upper = `/data/etc/upper`, work = `/data/etc/work`); `/tmp` on tmpfs (Alpine does not do this by default); `overlay` added to the kernel `modules=`. Before OpenRC starts services, `edel boot mount-data` adds the system users and groups the slot has but the upper `passwd`, `group` and `shadow` lack, since a machine's own copies would hide users a later slot adds (Duranium repairs this every boot); hostname, machine-id and password backups never come from the slot.
  Done when: boot-test greps `/ ... ro` from `/proc/mounts` printed on serial and `touch /usr/x` fails with EROFS; ab-test step 2 asserts a hostname changed in step 1 and the ssh host key fingerprint survived the update, and that a system user only the update image adds (in `ci/ab-test/files`) is in `getent passwd` after step 1 created a normal user. Notes: the real work is hunting stray writes to `/` service by service. OpenRC reads `/etc/rc.conf` early; if the sysinit ordering proves fragile, the fallback is our own init script passed with `mkinitfs -i FILE` (a copy of Alpine's initramfs-init with the `/data`, `/etc` overlay and `/var` mounts before switch_root), which is its own PR with a cargo-tested generator and a boot-test, since mkinitfs has no hook mechanism. The upper directory is the list of what this machine changed, and `edel settings export` lists it (AerynOS lesson 1).
- [x] **5. A hanging slot falls back too.** `edel boot guard` replaces the mark-good call in `edel-boot-ok`: an OpenRC service started first in sysinit (after devfs, before mdev and hwdrivers) with `command_background=yes` and a pidfile, so start() returns at once and the guard runs on in the background (a service that blocked until the default runlevel would wait for itself). It opens `/dev/watchdog`, pets it every second until every health file named by `EDEL_HEALTH` in `/usr/lib/os-release` exists (`default-runlevel` means `/run/edel/default-reached`, which `edel-boot-ok`, kept in the default runlevel with `depend() { after *; }`, touches; `compositor` later means `/run/edel/session/ready`) or `EDEL_HEALTH_TIMEOUT` (120 s) passes; healthy means mark-good, magic close and exit, so no daemon stays; timeout means stop petting, the hardware resets, GRUB counts the try. `/run/openrc/softlevel` is never consulted: OpenRC writes it at the start of a runlevel change, while services may still hang. `edel image build` writes the `EDEL_*` keys into os-release from `[image] health` and `health_timeout` in the definition (one standard file, no new format; the version joins it in M3). Kernel `modules=` adds `i6300esb` and `softdog`; `ci/vm.sh` adds `-device i6300esb -action watchdog=reset`; `panic=10` on the cmdline covers plain crashes.
  Done when: cargo tests show the health check accepts the sentinel files only, not softlevel; ab-test gains two cases: (hang) an update whose default runlevel has a service that blocks forever, so the sentinel never appears; (freeze) an update whose default runlevel disables panic reboot and runs `echo c > /proc/sysrq-trigger`. Both come back on the previous slot with the broken one at ok=0. Notes: the ab-test image sets `health_timeout = 30` (the i6300esb default period) so the six failed tries cost minutes, not a quarter hour; release images keep 120. The freeze case is what tests the hardware watchdog; softdog alone would catch the hang. Older QEMU spells it `-watchdog i6300esb -watchdog-action reset` (check in CI); check that linux-virt ships `i6300esb` as a module; laptops have iTCO, softdog is the fallback. Start the guard in sysinit when `/dev/watchdog` already exists there (the modules load from the initramfs), so a hang in sysinit or boot is caught too (check in CI). A kernel panic reboots through `panic=10`, and Alpine's initramfs panics instead of waiting at its recovery shell when `panic=` is set (checked 2026-10-02).
- [x] **6. Signed releases, two keys, no downgrades.** `release.toml` (format = 1: version, channel, date, `images[]` with name, file, sha256, size, min_size, loader_version) plus `release.toml.sig`; `edel release sign|verify` with ed25519 (`ed25519-dalek`; check the musl build in CI); two public keys baked at `/usr/share/edel/keys/` through `[release] public_keys` in the image definition; PR runs use a throwaway key; `edel update install` refuses a manifest that fails verification, an image whose sha256 differs, and a version not newer than the running slot unless `--allow-downgrade`. The manifest is the one file an old slot reads from the future, so its reader ignores fields it does not know (the signature still covers them) and refuses only a format it does not know; `docs/FORMATS.md` states the stepping-stone rule: a manifest format bump publishes the new format under a new file name and keeps `release.toml` pointing at a release whose `edel` reads both (ADR-008).
  Done when: cargo tests (sign then verify, tampered manifest, wrong key, downgrade, a signed manifest with an unknown extra field verifies and installs, one with `format = 2` is refused naming the format); ab-test refuses a manifest with one flipped byte (`refused: signature` on serial) and then installs the good one. Notes: one key scheme for images, add-ons and manifests. A machine two formats behind installs the stepping stone, then the newer release at its next check, with no extra command (AerynOS users rerun theirs by hand). The second key exists from the first install so a rotation never strands a machine; the real key moves to a GitHub secret in M3 and an offline backup is Alimardon's job.
- [x] **7. Update from a URL, compressed, any slot size.** `edel update install URL` and `edel update check` (`ureq` with rustls, `flate2` for gzip), streaming the `.ext4.gz` into the slot while hashing; `edel image build` shrinks the slot image with `resize2fs -M` before gzip and records `min_size`, and emits `.ext4.gz` and `.img.gz` next to the raw files; install refuses an image whose `min_size` exceeds the slot and runs `resize2fs` on the target partition after the write, so a small image fills any slot; `ci/ab-test.sh` serves `out/` with `python3 -m http.server` on the runner and the VM reaches it at 10.0.2.2.
  Done when: ab-test step 1 installs from `http://10.0.2.2:8000/release.toml` with no second disk, using an update built with a smaller `slot_mib` than the running disk, and the VM boots it with `df /` showing the full slot; sizes.sh shows compressed sizes. Notes: rustls on musl, prefer the ring provider (check in CI); `file://` paths stay for USB installs; no delta updates until a measurement says the base is too big.
- [x] **8. The bootloader rides along in the update.** `edel image build` places the GRUB EFI binary, `grub.cfg` and a `loader.toml` (version = hash of both) under `/usr/lib/edel/boot/` in the rootfs; `edel update mark-good`, only after the slot is confirmed, compares with the ESP's `loader.toml` and installs the new loader by write to `.new`, fsync, rename, keeping `BOOTX64.EFI.prev`. `grub.cfg` stays compatible with both slots.
  Done when: ab-test builds the update image with `--loader-tag ci` so its loader differs; after the slot boots and is confirmed the ESP's `loader.toml` shows the new version; cargo test for the rename sequence in a tempdir. Notes: the loader is the one piece outside the A/B rollback: firmware loads one `BOOTX64.EFI`, and if it does not start, no slot is reachable and `.prev` only helps a person with a USB stick. The protection is that every loader transition is exercised in CI (M3.5 boots the old preview's ESP through the swap and once more) and that loader changes stay rare and reviewed; swap after confirmation, never at install time; the env block is never replaced; UEFI only. Call `syncfs` after the write and after the rename: a rename on FAT is not guaranteed atomic (AerynOS's blsforme works around vfat corruption).
- [x] **9. Flatpak on the musl base, checked early (standalone spike).** A CI-only definition `ci/flatpak/vm.toml` (vm plus flatpak, bubblewrap, dbus); `ci/flatpak-test.sh` adds Flathub as user `ci` (`flatpak --user`, the default for every later app install, so the data lives in `/home` and no polkit is needed), installs `org.freedesktop.Platform` (current branch, check), runs `flatpak run --command=sh org.freedesktop.Platform -c 'echo hello from glibc'`, and installs the oldest runtime Flathub still serves; `docs/SPIKE-flatpak.md` records the verdict, download sizes, whether unprivileged user namespaces work with Alpine's kernel config, and what `apk info -R flatpak` says about polkit arriving anyway.
  Done when: serial shows `hello from glibc` for the newest runtime, and the oldest runtime's result is recorded in `docs/SPIKE-flatpak.md`. Notes: no GUI and no compositor needed, so it runs now and retires the ADR-003 and ADR-005 risk for a few CI minutes.
- [x] **10. No watchdog, still no stuck slot.** When `edel boot guard` finds no watchdog at all (a cloud VM that offers none, a kernel without softdog such as linux-virt), it restarts the machine itself once `EDEL_HEALTH_TIMEOUT` passes, after `sync`, so GRUB counts the try exactly as a watchdog reset would; with a watchdog it behaves as today. Found by the outside review of 2026-10-06 (R1): today the guard prints that the watchdog will restart the machine and exits, and with no watchdog nothing does.
  Done when: cargo tests for the choice (a watchdog, softdog only, none); an ab-test case boots an update whose default runlevel hangs, with QEMU's watchdog device left out, and the VM comes back on the previous slot with the broken one at ok=0. Notes: a reboot from user space can itself wait on a hung service, so the guard forces it (`reboot -f`, check in CI). Done with: the guard calls `sync` and the `reboot` system call itself, which is what `reboot -f` does, with no program to start; ab-test's hang step (step 4 to 5) now runs slot B without its watchdog drivers, as the VM's linux-virt has no softdog, and the freeze step still proves the hardware watchdog.
- [x] **11. Images name their own health checks.** A feature's `health` may name any check, not only `default-runlevel` and `compositor`: a check is a sentinel `/run/edel/health/NAME` that the feature's own service writes, such as a server's `network` once its default route answers or an edge device's job once it runs, and `edel image check` refuses a health name that no feature in the image writes. The guard waits for all of them as today, so an update that breaks a server's network falls back instead of being confirmed (R5 of the 2026-10-06 review, ADR-009).
  Done when: cargo tests for the names and the refusal; an ab-test case whose update breaks the network names `network`, the check never passes, and the VM comes back on the previous slot. Notes: the two names of today keep their files (`/run/edel/default-reached`, `/run/edel/session/ready`); a check must finish well inside `health_timeout`. Done with: a feature's file writes `$health_dir/NAME`, which `edel image check` looks for in the image's features' files; the guard's timeout line names the checks not reached; no image lists a check of its own yet, so ab-test's network case adds `network` to slot B's os-release with a service of its own, and takes the networking service out.
- [x] **12. Slots stay byte-identical after install.** GRUB and fstab find a slot by its partition (GPT partition label or PARTUUID), never by its filesystem UUID; `edel install` and `edel update` write a slot image unchanged, with no new filesystem UUID and no resize2fs (a read-only root needs no free space), so a slot's bytes stay those that were signed for its whole life and a verified root (M11.1) can check them at every boot (ADR-009). A disk-layout change, recorded in `docs/FORMATS.md`.
  Done when: install-test and ab-test pass, and a new check finds that slot A of the installed disk, and slot B after the update, hash to exactly the image that was written. Notes: two slots holding the same image share a filesystem UUID, so nothing may find a slot by it (`/dev/disk/by-uuid` included, check in CI); the new `grub.cfg` reaches machines installed earlier with the loader (M1.8), and M3.5 proves it once a preview exists. Done with: GRUB's `probe --part-uuid` and `root=PARTUUID=`; Alpine's initramfs finds that partition but busybox `mount` cannot take `PARTUUID=` (the first run panicked at "Mounting root: failed"), so the image builder hands `mkinitfs -i` Alpine's own init with one change, generated at each build and refused when Alpine's init no longer has its place, that reads the device from the kernel's partition events; `edel update` checks a slot with `e2fsck -fn`, which writes nothing; a slot's file system has no journal (`mkfs.ext4 -O ^has_journal`), since Linux writes a journal's superblock at every mount, read-only ones too, and the second run found a booted slot B 6 bytes off its image there; an image's slot A is its update image itself; install-test wants the installer's `slot A is the running slot byte for byte`, and ab-test hashes slot B after it booted against `release.toml` and finds both slots their shrunk size. Nothing in the images reads `/dev/disk/by-uuid` (the data partition is partition 4, the ESP its label).
- [x] **13. The clock is right on every machine.** The `machine` feature sets the clock from the network with busybox `ntpd` (no new package) once the network is up, and again daily where crond runs; a settings file key, named in the step (ADR-008), gives other servers, such as a cloud provider's own, absent meaning `pool.ntp.org`. A laptop whose clock battery died otherwise fails every certificate check, so updates over `https://` fail (R4 of the 2026-10-06 review).
  Done when: boot-test starts a VM whose clock QEMU sets years back (`-rtc base=2020-01-01`) and serial shows the right year once the network is up (the runner's network, check in CI). Notes: no time daemon stays running on desktops; servers may keep `ntpd` running, which their uptime serves. Done with: the key is `region.time_servers`, one to four host names on the Region page beside the time zone; the `machine` feature's `edel-clock` service starts `/usr/libexec/edel-clock` in the background after the network, which runs `ntpd -n -q` with up to 20 s, up to three times 5 s apart (since 2026-10-08, after a CI runner's first try went unanswered), prints one line and writes the hardware clock, so no image keeps a time daemon and nothing waits for it; no feature runs crond, so there is no daily re-sync yet (each start sets the clock); boot-test's third boot starts the VM in 2020 and wants 2026 or later.

## M2 (phase 1, now): One file describes and installs a machine

- [x] **1. Settings file format v1.** `crates/edel/src/settings.rs`: `format = 1`, `[system]` channel/version/variant/developer/profiles, `[users.NAME]` admin/ssh_keys/shell, `[network]` hostname, `[region]` language/keyboard/timezone, `[layout]` preset/tiling/title_bars/device_type, `[displays.NAME]` position/scale/mode/enabled/transform, `[appearance]` wallpaper/color_scheme/accent/font/font_size/cursor_size/icon_size/motion, `[shortcuts]` action = keys, `[default_apps]` browser/files/editor/terminal/mail, `[startup]` apps, `[power]` lid/idle/power_button/on_battery, `[services]` name = true or false, `[updates]` auto/window, `[apps]` flatpak, `[addons]` add (the three customization levels of ADR-007: everything here is level 1); serde without `deny_unknown_fields`, in a library target `edel::settings` inside `crates/edel` whose network and signing dependencies sit behind the binary's default `cli` feature, so the compositor (M4.5), shell-ui (M5.1) and Settings (M5.6) parse with the same code and the same defaults table; unknown keys are collected with `serde_ignored` (check in CI) and enum-valued keys are parsed leniently (an unknown value or a wrong type falls back to the default and is reported, through a `#[serde(other)]` variant or a string mapped after parsing); `edel settings check FILE` refuses an unknown key, value or format, naming the key and listing the allowed values, while the boot reader applies the rest and reports it; a cargo test fails when the structs lack a key listed in the committed, append-only `crates/edel/tests/keys.txt`, and CI fails a PR that deletes a line of it without bumping the format (ADR-008); `docs/settings.md`. Keys that later milestones fill in are parsed now; check and set refuse them with "not supported yet", while the boot apply skips them and reports them, so adding them is not a format bump. Every loader `edel` owns checks `format`; checkers refuse an unknown format with a clear message, while the boot reader that meets a newer `settings.toml` reads `settings.toml.v<N>` beside it for its own N (left by `edel migrate` at a bump) or applies nothing and says so; a key is never removed or renamed within a format (a dropped key stays parsed and is reported as no longer used; an unavoidable rename reads both names); a value naming a preset, profile, add-on or feature this release lacks falls back to the default and is reported, never failing boot; `docs/FORMATS.md` states these rules. ADR-006's example is renamed from `[extensions]` to `[addons]` in the same PR.
  Done when: cargo tests parse the ADR-006 example; `edel settings check` rejects `appearance.acent` naming the key, rejects `appearance.mode = "sepia"` listing light, dark and auto, and rejects format 2, while the boot read of the same file applies every other key, uses the default scheme and reports both; a `settings.toml.v1` beside a format-2 file is used, and with none nothing is applied; a key removed from the structs fails against `keys.txt`; everything round-trips through `toml::to_string`. Notes: `edel migrate` arrives with the first real format bump, when there is a real old file to test on (AerynOS lesson 2); a registry before that is machinery no principle asks for.
- [x] **2. `edel settings apply`, at boot and on demand.** Applies hostname, users (busybox adduser; admin means the `admin` group; users without a password get `*` in `/etc/shadow`, never adduser's `!`, which OpenSSH treats as a locked account), `~/.ssh/authorized_keys` and the developer flag; OpenRC boot service `edel-settings` with `depend() { before hostname; need localmount; }` applies the offline sections of `/data/edel/settings.toml`, seeded on first boot in this order: a volume labelled `EDEL-SEED` holding `settings.toml`, `/EFI/edel/settings.toml` on the ESP, `/usr/share/edel/settings.toml`; idempotent. Sections that need the network (`[apps]`) are applied only when a user or Settings calls apply, in the background.
  Done when: `ci/system-test.sh` builds a VM with a seed file creating user `ci` with a CI-generated ssh key, boots with `hostfwd=tcp::2222-:22`, `hostname` on serial equals the seed's value on the first boot, and `ssh -p 2222 ci@localhost edel settings export` succeeds; cargo test for the shadow line. Notes: apply never deletes users it did not create; password hashes live in the `/etc` overlay on `/data`, never in the file.
- [x] **3. `edel settings export`, `diff`, `set` and `reset`.** Export writes `settings.toml` plus the list of files in `/data/etc/upper`; diff is a dry run of apply and exits 0 when there is nothing to do, listing not-yet-installed apps as pending rather than drift; `edel settings set KEY=VALUE` edits one key in place with `toml_edit`, so comments, order and keys this slot does not know survive byte for byte (the compositor and Settings use it from M4 on); `set` refuses an unknown key or value it is asked to write, keeps and reports unknown keys already in the file, and on a newer-format file changes `settings.toml.v<N>` and says the change applies to this release only; `unset KEY` removes a key, and apply enforces the release default for every absent key it owns, taken from the defaults table in `edel::settings` filled from the slot (for a file in the `/etc` overlay such as `/etc/hostname`, by removing the upper copy); no writer ever writes a default; diff also lists ignored keys, unknown values and unknown names (ADR-008).
  Done when: system-test: apply, export, diff is empty; `edel settings set network.hostname=other` and diff shows exactly that one change; after `unset network.hostname` and apply, `hostname` prints the image's hostname; a line `future.key = 1` and a hand-written comment above `[users.ci]` survive the set and the unset byte for byte.
- [x] **4. `edel install DISK --settings FILE`.** Partitions the target with `boot.rs` Layout, copies the running slot's partition to slot A with a fresh UUID, writes the ESP from `/usr/lib/edel/boot` and an initial grubenv, creates `edel-data` and puts the settings file in it; refuses the disk it runs from. `sfdisk`, `dosfstools` and `mtools` join `images/vm.toml` (today they live only on the build host). Install builds one plan in `edel::settings` (the disk's model and size, and its partitions with labels and filesystems, such as `Windows (NTFS, 420 GB)`) and uses it three ways: `--dry-run` prints it and changes nothing, a terminal run prints it and asks the person to type the disk's name, and a run with neither a terminal nor `--yes` prints it and exits 3 (ADR-008).
  Done when: `ci/install-test.sh` boots the VM image with a blank second virtio disk, a test service (`command_background=yes` and a pidfile like the guard, waiting until `edel update status` shows the running slot confirmed, so the guard never waits on it) first runs `edel install /dev/vdb --settings /usr/share/edel/ci/install.toml` without `--yes` (serial shows the plan and exit code 3, vdb's sha256 is unchanged) and then with `--yes`, QEMU then boots vdb alone to the file's hostname at the login prompt with slot A confirmed and ssh host keys that differ from the live image's; a cargo test asserts the install plan uses only tools listed in the image definition. Notes: no ISO; the disk image written to a USB stick is the live medium and the installer; copying the running slot avoids carrying a payload inside a slot.
- [x] **5. Fresh install plus update plus rollback, required.** `ci.yml` runs install-test and then ab-test against the installed disk; docs say the job is required for merging (branch protection is a repository setting Alimardon turns on).
  Done when: a test branch that breaks a first-boot service fails the job. Notes: AerynOS lesson 3, enforced rather than remembered.

## M3 (phase 1, now): Release train, kept small

- [x] **1. Version, channel, platform level and package record inside the image.** `/usr/lib/os-release` gains `VERSION_ID` and `EDEL_CHANNEL`, `EDEL_ARCH`, `EDEL_LOADER_VERSION`, `EDEL_PLATFORM_LEVEL` next to the `EDEL_HEALTH` keys from M1.5; the version `YYYY.MM.N` comes from the runner (`git describe --tags` in ci.yml, passed as `EDEL_VERSION`; the build container has no git and the checkout is another uid's), so `edel image build` stays deterministic; the build writes the installed package list (`apk list --installed`) to `/usr/share/edel/packages` and `out/<image>.packages`; the PR summary shows the diff against the last preview, as a record, never a gate; `edel update status` shows running and available versions; every image of one CI run installs from one package snapshot, so images of one release cannot differ (Duranium does this).
  Done when: boot-test greps the version from serial; cargo tests for parsing and ordering; the diff appears in the step summary. Notes: apk has no lockfile and a true lock would need a mirror, a part we reject; the monthly rebuild in M8 is the bump.
- [x] **2. Budgets enforced.** `ci/budgets.toml` (container tar.gz MiB, VM slot used MiB, boot to the mark-good line in seconds read from `/proc/uptime` inside the guest, idle used memory MiB from `/proc/meminfo` printed on serial), first values from measurement plus 20 percent; `ci/sizes.sh` takes the median of three boots before comparing, fails the job when exceeded and writes the summary table.
