# CI scripts

`.github/workflows/ci.yml` (workflow "CI") runs on every pull request (opened, pushed to, reopened or marked ready), every push to `main` and every `v*` tag; a new push to a pull request cancels that pull request's older run. Its first job, "What this change can affect", runs `changes.sh` (CI speed-ups, 2026-10-16): a push or tag runs everything, a draft runs "Rust checks" only unless it has the label `full-ci` (add it, then push), and otherwise the changed paths decide whether the image build and VM tests and the desktop tests run; a job it skips is joined by its check, which passes, so the four checks a merge waits for always report. "Rust checks" (the commands in the root CLAUDE.md) runs on every change. "Build and boot images" joins "Build images" (the build, the container, initramfs and release checks and the budget boots, `sizes.sh`, alone on its runner) and the VM test lanes, one "VM tests LANE" job each, fed by the build job's artifacts `edel-vm-images-NAME`, one per archive (`vm-tests.sh pack`, kept one day), so each lane downloads only its own, each lane's logs kept as `edel-vm-LANE`. Beside them run the desktop tests, four "Desktop part" jobs at once (M6.17) joined by "Desktop tests", which prints the basics checklist from their passed cases, and "Desktop on another distribution" (M5.15a, `elsewhere-test.sh`, which builds the compositor, shell-ui and the test client against Ubuntu's own libraries, its `target` cached on `Cargo.lock`). There is no toolchain pin; the images job caches `.cargo-home` and `target`, keyed on `Cargo.lock`. A third job, "Publish the release", runs after both on a push to `main` or a tag, only when the repository variable `EDEL_PUBLISH` is `yes` (M3.4, `docs/RELEASE.md`), and a fourth, "Publish the docs site", after both on a push to `main` only when `EDEL_SITE` is `yes` (M8.10a); they have the only write tokens. Every action is pinned by commit digest with its release in a comment, and the build and signing containers by the digest in `features/base.toml`'s `[alpine]` (`image_digest`, M3.9); to bump an action look its new tag up with `git ls-remote --tags https://github.com/actions/NAME`, and the image with `docker buildx imagetools inspect alpine:BRANCH`. `.github/workflows/release.yml` (workflow "Release") runs when a release made from a `v*` tag is published and moves the stable channel (`channel.sh publish`).

Every script, what it does and what it needs is in [SCRIPTS.md](SCRIPTS.md), one table row per script; what each desktop test case checks is in [CASES.md](CASES.md), one line per case. A pull request that changes a script or a case edits its own row or line there.

## Rules

- Run every script as `sh ci/NAME.sh` from the repository root, as CI does; `ab-test.sh` and `vm.sh` are not executable, and all of them use relative paths.
- CI numbers each build `YYYY.MM.N` with N the run number (step "Number this build") and passes it into the build container as `EDEL_VERSION`; the A/B update is that version plus `.1`, so it is newer.
- On the runner, CI installs QEMU, OVMF and the initramfs check's tools with `sudo apt-get update && sudo apt-get install -y qemu-system-x86 ovmf cpio zstd`, after an "Enable KVM" step that opens `/dev/kvm` with a udev rule.
- Write POSIX sh that both busybox (`build.sh` runs in Alpine) and dash (the tests run on the Ubuntu runner) accept: `#!/bin/sh`, `set -eu`, tabs, quoted expansions, no bashisms, a header comment saying what the script does and why.
- Never run `build.sh` outside the `alpine:3.24` container: it needs apk, root and the host keys in `/etc/apk/keys`.
- The A/B test runs its steps inside the VM from an OpenRC service; what each step checks is in [SCRIPTS.md](SCRIPTS.md#the-ab-tests-steps).
- VM tests leave the built images unchanged: they open them with `-snapshot`, or boot a copy they delete afterwards (`flatpak-test.sh`). `ab-test.sh` leaves out `-no-reboot` because the VM restarts between steps.
- A new VM case follows the same pattern: a test-only service inside the image and a serial line the host script waits for.
- Test-only files live under `ci/`, never in `images/` or `features/`. They reach an image through `edel image build --files DIR`, or, when a test needs other packages or definition keys, through a CI-only definition under `ci/` with its own features in a `features/` beside it (`ci/flatpak/vm.toml` and `ci/flatpak/features/flatpak-test.toml` since M1.9 and M4.0, `ci/features/ci-hello.toml` in M7.2a; the A/B image takes its 30 s timeout from `edel image build --health-timeout 30`, not from a definition). Release definitions never point into `ci/`.
- The tests grep exact strings: serial markers, `edel status` lines, `/etc/issue`, `PRETTY_NAME`, the `edel` hostname. Change a string and its grep in the same PR.
- Budgets live in `ci/budgets.toml`, one number per key; lower one in a reviewed change, and never raise one to make a pull request pass. A budget failure on a change that cannot have caused it is run once more, and otherwise reported, not relaxed.
- Timeouts: `BOOT_TIMEOUT` (300 s, also each budget boot), `AB_TEST_TIMEOUT` (1500 s), `INSTALL_TEST_TIMEOUT` (600 s), `FLATPAK_TEST_TIMEOUT` (1800 s), `DESKTOP_TEST_TIMEOUT` (300 s) and `DESKTOP_ROLLBACK_TIMEOUT` (240 s, each of the rollback case's waits). With KVM (measured 2026-10-02 on #33) the image job takes about 8.5 minutes: build 175 s, both lanes of VM tests 251 s (the A/B test 200 s, the Flatpak test about 50 s), budget boots 34 s; the VM reaches the login prompt in about 12 s. Boot times in the budgets are only honest with KVM.
- CI keeps `out/*.tar.gz`, `out/*.log`, `out/*.packages`, `out/*.cdx.json` (M8.12) and the desktop tests' screenshots `out/desktop-test/*.png` and `out/desktop-live/*.png` (artifact `edel-images`; the VM test lanes' logs and the live and fresh lanes' screenshots are each lane's `edel-vm-LANE`), and on a push to `main` the desktop disk with `SHA256SUMS` (artifact `edel-try-x86_64`, 14 days, M3.6); the other VM disks are not uploaded, so a VM test cannot be rerun from CI outputs. On a failure, read the job log: the tests print the serial log.
- Measure a CI speed change on a full run before keeping it, step by step from the job logs (CI speed-ups, 2026-10-16): the first lane split put the stick and the fresh disk in one `live` lane of 20 minutes and every lane downloaded every lane's images (6 GiB), which made the images path slower than before; the lanes and their archives are now split so the longest lane sets the time.
- The build container gets `SOURCE_DATE_EPOCH` (M8.6), which other tools read too: fc-cache wrote no fonts' cache with it, so `bake_font_cache` runs fc-cache without it. A build step that starts failing after a change of that date may be another such tool. A local check of a container image's reproducibility needs no VM: build `images/container.toml` twice in the `alpine:3.24` container with the same `SOURCE_DATE_EPOCH` (about 2 s each once cargo has built `edel`) and compare.
- A check that needs apk (version order, the index) runs in the build container, `docker run ... "$ALPINE"`, as `bom.sh advisories` does (M8.12): Ubuntu has no apk, and its version rules are apk's own. Name `shell: bash` on a step that pipes into `tee`: without it a step runs `bash -e` with no pipefail, and the pipe hides a failure. Locally the container reaches Alpine and secdb through the session's proxy with `--network host`, the proxy's variables and its CA bundle mounted at `/etc/ssl/certs/ca-certificates.crt`. A check against a database that moves (secdb, RustSec) fails only on what a rebuild would fix, never on what upstream has not published.
- Cloud sessions (2026-10-16) have no KVM (no `vmx` or `svm`), so the VM tests run only under TCG, far too slowly to try a lane; a local `build.sh` needs `docker run --network host`, the proxy's variables and its CA bundle mounted and named by `SSL_CERT_FILE` and `CARGO_HTTP_CAINFO`, takes about 27 minutes and can fill the session's disk. Check scripts with `sh -n`, `dash -n` and `changes.sh --self-test`, and prove the rest on the pull request.
- "Build and boot images" is the job that must pass before a merge: once Alimardon turns on branch protection for `main` (M2.5), GitHub refuses to merge while it is red.
- After a real build, `out/work/` and the `work/` directories under `out/install-test/`, `out/system-test/`, `out/ab-test-update/`, `out/flatpak/` and `out/desktop-test/` stay owned by root; a local container run also leaves `target/` owned by root. Deleting them needs root.
