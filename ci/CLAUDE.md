# CI scripts

`.github/workflows/ci.yml` (workflow "CI") runs on every pull request, every push to `main` and every `v*` tag; a new push to a pull request cancels that pull request's older run. Its two jobs run in parallel on `ubuntu-latest`: "Rust checks" (the commands in the root CLAUDE.md) and "Build and boot images" (the scripts here). There is no toolchain pin; the images job caches `.cargo-home` and `target`, keyed on `Cargo.lock`. A third job, "Publish the release", runs after both on a push to `main` or a tag, only when the repository variable `EDEL_PUBLISH` is `yes` (M3.4, `docs/RELEASE.md`), and a fourth, "Publish the docs site", after both on a push to `main` only when `EDEL_SITE` is `yes` (M8.10a); they have the only write tokens. Every action is pinned by commit digest with its release in a comment, and the build and signing containers by the digest in `features/base.toml`'s `[alpine]` (`image_digest`, M3.9); to bump an action look its new tag up with `git ls-remote --tags https://github.com/actions/NAME`, and the image with `docker buildx imagetools inspect alpine:BRANCH`. `.github/workflows/release.yml` (workflow "Release") runs when a release made from a `v*` tag is published and moves the stable channel (`channel.sh publish`).

## Rules

- Run every script as `sh ci/NAME.sh` from the repository root, as CI does; `ab-test.sh` and `vm.sh` are not executable, and all of them use relative paths.
- CI numbers each build `YYYY.MM.N` with N the run number (step "Number this build") and passes it into the build container as `EDEL_VERSION`; the A/B update is that version plus `.1`, so it is newer.
- On the runner, CI installs QEMU, OVMF and the initramfs check's tools with `sudo apt-get update && sudo apt-get install -y qemu-system-x86 ovmf cpio zstd`, after an "Enable KVM" step that opens `/dev/kvm` with a udev rule.
- Write POSIX sh that both busybox (`build.sh` runs in Alpine) and dash (the tests run on the Ubuntu runner) accept: `#!/bin/sh`, `set -eu`, tabs, quoted expansions, no bashisms, a header comment saying what the script does and why.
- Never run `build.sh` outside the `alpine:3.24` container: it needs apk, root and the host keys in `/etc/apk/keys`.
- The A/B steps run inside the VM from the OpenRC service `ab-test/files/etc/init.d/edel-ab-test` (a committed runlevel link enables it; it needs `edel-boot-ok`). It keeps its step number in `ab-test-step` on the EFI system partition and downloads every update from `http://10.0.2.2:8000/`. On a boot with a second disk (the install test's live boot) the service does nothing. Step 1 checks the read-only root, expects `refused: expired` for `expired.toml` and `refused: signature` for `bad.toml` (every `edel update` there passes `--allow-http`, M3.8), writes markers into `/home` and `/var`, deletes `/var/lib/ci-new`, changes the hostname with `edel settings set` and `apply`, notes the ssh host key, adds a user, drops a system user from the machine's `/etc/passwd` and installs into slot B; step 2 expects all of that kept, slot B still the signed image byte for byte (the first `size` bytes of its partition hash to `release.toml`'s `sha256`, after it booted) and its file system its shrunk size (`df -m /` under 1024, as slot A's in step 1, M1.12), its tagged boot loader on the ESP with `BOOTX64.EFI.prev` kept, the dropped system user and `/var/lib/ci-new` back from the slot, and rolls back to slot A by command; step 3 expects the markers and slot A's loader back on the ESP, installs into slot B again and breaks its initramfs; step 4 expects `B: ok=0 try=3`, the markers and `from = "B"` in `/data/edel/last-fallback.toml`, checks that a rollback to slot B is refused and installs slot B again with a service that hangs and without its watchdog drivers (`lib/modules/*/kernel/drivers/watchdog/` emptied, as linux-virt has no softdog), so it boots with no watchdog at all; step 5 expects slot B off after the guard restarted it itself (M1.10; `ab-test.sh` wants the guard's `the machine has no watchdog; restarting it now` on serial) and installs it again with a service that freezes the kernel with panic reboots off; step 6 expects slot B off again and installs it again with the health check `network` added to its os-release, a service that writes `$health_dir/network` once a default route exists, and neither its networking service nor this test's; step 7 expects slot B off again (M1.11; `ab-test.sh` wants the guard's `health not reached after N s: network`) and prints `AB-TEST: PASS`. Step 4 proves GRUB's count of three tries; for the hang and freeze cases the test sets `B_TRY=2` in the ESP's `grubenv` after installing (the same length, so the block stays 1024 bytes), so each takes one try, about 170 s less per run. The install test image and the A/B update are built with `--health-timeout 30`. A mismatch prints `AB-TEST: FAIL: step N expected "LINE"` and powers off.
- VM tests leave the built images unchanged: they open them with `-snapshot`, or boot a copy they delete afterwards (`flatpak-test.sh`). `ab-test.sh` leaves out `-no-reboot` because the VM restarts between steps.
- A new VM case follows the same pattern: a test-only service inside the image and a serial line the host script waits for.
- Test-only files live under `ci/`, never in `images/` or `features/`. They reach an image through `edel image build --files DIR`, or, when a test needs other packages or definition keys, through a CI-only definition under `ci/` with its own features in a `features/` beside it (`ci/flatpak/vm.toml` and `ci/flatpak/features/flatpak-test.toml` since M1.9 and M4.0, `ci/features/ci-hello.toml` in M7.2a; the A/B image takes its 30 s timeout from `edel image build --health-timeout 30`, not from a definition). Release definitions never point into `ci/`.
- The tests grep exact strings: serial markers, `edel status` lines, `/etc/issue`, `PRETTY_NAME`, the `edel` hostname. Change a string and its grep in the same PR.
- Budgets live in `ci/budgets.toml`, one number per key; lower one in a reviewed change, and never raise one to make a pull request pass. A budget failure on a change that cannot have caused it is run once more, and otherwise reported, not relaxed.
- Timeouts: `BOOT_TIMEOUT` (300 s, also each budget boot), `AB_TEST_TIMEOUT` (1500 s), `INSTALL_TEST_TIMEOUT` (600 s), `FLATPAK_TEST_TIMEOUT` (1800 s), `DESKTOP_TEST_TIMEOUT` (300 s) and `DESKTOP_ROLLBACK_TIMEOUT` (240 s, each of the rollback case's waits). With KVM (measured 2026-10-02 on #33) the image job takes about 8.5 minutes: build 175 s, both lanes of VM tests 251 s (the A/B test 200 s, the Flatpak test about 50 s), budget boots 34 s; the VM reaches the login prompt in about 12 s. Boot times in the budgets are only honest with KVM.
- CI keeps `out/*.tar.gz`, `out/*.log`, `out/*.packages` and the desktop tests' screenshots `out/desktop-test/*.png` and `out/desktop-live/*.png` (artifact `edel-images`), and on a push to `main` the desktop disk with `SHA256SUMS` (artifact `edel-try-x86_64`, 14 days, M3.6); the other VM disks are not uploaded, so a VM test cannot be rerun from CI outputs. On a failure, read the job log: the tests print the serial log.
- "Build and boot images" is the job that must pass before a merge: once Alimardon turns on branch protection for `main` (M2.5), GitHub refuses to merge while it is red.
- After a real build, `out/work/` and the `work/` directories under `out/install-test/`, `out/system-test/`, `out/ab-test-update/`, `out/flatpak/` and `out/desktop-test/` stay owned by root; a local container run also leaves `target/` owned by root. Deleting them needs root.
