# CI scripts: what each does

One row per script (moved here from [CLAUDE.md](CLAUDE.md) by M6.17, line 11, which keeps the rules). A pull request that changes a script edits its own row.

| Script | What it does | Needs |
|---|---|---|
| `apt.sh` | `sh ci/apt.sh PACKAGE...`, in every CI job that needs Ubuntu packages (the libraries, Xvfb, QEMU and OVMF): `apt-get install` with its downloads kept in `~/.cache/edel-apt`, which `actions/cache` keeps per job and month, so a run downloads only what changed; Ubuntu's mirror for the runners sometimes took 20 minutes for QEMU's 45 MB | `sudo` and `apt-get` on an Ubuntu runner |
| `pull-alpine.sh` | Pulls the build container named by `features/base.toml` (`$ALPINE`) from `mirror.gcr.io` first and Docker Hub second, three tries each, and writes the reference that worked to `$GITHUB_ENV`; Docker Hub's anonymous pull limit stopped three runs on 2026-10-09 | Docker, and either registry |
| `build.sh` | Installs the build tools, in up to three tries (`apk add --no-cache cargo dosfstools e2fsprogs e2fsprogs-extra grub grub-efi merge-usr mtools openssh-keygen pigz qemu-img sfdisk tar flatpak pipewire-tools pulseaudio-utils eudev-dev libinput-dev libseat-dev libxkbcommon-dev mesa-dev pkgconf gtk4.0-dev libadwaita-dev`, pigz for `edel image build`'s `.gz` files, qemu-img for its `.qcow2` disk (M7.4), merge-usr for the `/usr`-merged roots it makes (M7.1), flatpak for the default apps it installs (M6.2), pipewire-tools and pulseaudio-utils for the `pw-record` and `parecord` of the test runtime (`apps/make-repo.sh`), the `-dev` packages for the compositor and Settings; the lists are for the images' channel and expire 60 days after signing), builds `ci/apps-test/vm.toml` into `out/apps-test/` (default app TestA, `--apps-url http://10.0.2.2:8002/`) and its update into `out/apps-test-update/` (TestB, `--dropped-app org.edel.TestA`) with the signed list in `out/apps-test/update/` (M6.2), builds `ci/flatpak/vm.toml` into `out/flatpak/` and `ci/desktop/vm.toml` into `out/desktop-test/` (`--health-timeout 30` and the first public key, M4.8; its default apps, M6.2, the test app `org.edel.TestA` from `out/apps-repo`, which `apps/make-repo.sh` makes first) with its update directory `out/desktop-test/update/` (its own update image and a `release.toml` for version `VERSION.1` signed with the first key, which `desktop-test.sh rollback` serves), builds `images/container.toml` into `out/desktop-container/` (M7.6b part 4: the profile-developer case's container image, which desktop-test.sh serves), builds the fleet (M7.3): `out/fleet-a/` and `out/fleet-b/`, the VM image with `--settings ci/fleet/base.toml --settings ci/fleet/device-a.toml` (or `device-b.toml`, whose `[install]` makes it a stick that installs itself), and `out/fleet-seed.img`, a 4 MiB FAT `EDEL-SEED` volume holding `ci/fleet/erase.toml`, builds the server (M7.4): `ci/server/vm.toml` into `out/server-test/` (`--no-compress`, `--health-timeout 30`), its seed `out/server-test/seed.img` (a 4 MiB FAT `EDEL-SEED` volume) and the user data `out/server-test/user-data.toml`, then makes `out/install-file.img`, a 4 MiB FAT stick (`mkfs.vfat`, `mcopy`) holding `ci/desktop/install-file.toml` as the settings file for `desktop-test.sh live` (M6.6b), then makes the release (M3.4): `out/release/` with the update images, their `release.toml` (whose `[[downloads]]` gives the sum of every other file, `--download`, M8.10b), the disks (`.img.gz` and `.qcow2`), the container image and the package lists, and `out/channel/release.toml` naming the update images by URL under the release of `EDEL_TAG` (or `v` and the version), both unsigned (`sign.sh` signs them); | `repro-check.sh` | After `build.sh` (M8.6), which builds the container image a second time into `out/repro/`, and the CI VM image (`ci/vm/vm.toml`) twice, into `out/repro/first/` and `out/repro/` (the released `images/edel.toml` would fetch its apps twice) from the same commit (`SOURCE_DATE_EPOCH`, from the workflow's step "Date the build by its commit"): compares each pair by sha256, prints one line each and a `### Reproducible images (M8.6)` table to the run summary, and fails when the container images differ; the VM slot is reported only, as mkfs.ext4 still gives it a random UUID and hash seed | A real build |
| `bom.sh` | Each image's bill of materials (M8.12, ADR-009), which `edel image build` writes as `out/IMAGE.cdx.json` (CycloneDX 1.6: every package with its version, licence, purl and apk origin) from the same read of apk's database as `out/IMAGE.packages`; the release publishes both. `validate`, on the runner: a `.cdx.json` beside every `.packages`, each valid against the CycloneDX schema (`cyclonedx-python-lib`, pinned in the script, in a venv at `out/bom-venv`), a `### Bills of materials (M8.12)` table to the run summary. `advisories`, in the build container: fetches Alpine's security database (secdb) for `features/base.toml`'s branch and the index, and lists each image's source packages that lack a fix (`apk version -t`), one row per image and source package under `### Security fixes (M8.12)`; it fails when Alpine already ships the fix (rebuild: the build takes the newest packages) and only lists a fix whose package Alpine has not published yet. `--self-test` runs the same check on planted fixtures, in the same container | python3 and pip's index (`validate`); apk, jq and secdb (`advisories`) |
| `initramfs-check.sh` | For every definition in `images/` with a `[vm]` kernel: checks its `/boot/config-*` for every option `ci/kernel-options.toml` requires of that flavour (each with a reason; `kernels` limits one to some flavours), and lists the modules in its initramfs (gzip or zstd cpio), failing when an `lts` image's lacks `nvme`, `usb_storage`, `xhci_pci`, `ahci`, `mmc_block`, `sdhci_pci` (eMMC disks), `ext4` or `overlay`, holds a graphics driver that needs firmware (`amdgpu`, `i915`, `xe`, `radeon`, `nouveau`: the root loads them with their firmware, M8.17e) or is over `initramfs_mib` (`budgets.sh`), or the VM's lacks `virtio_blk`, `ext4` or `overlay` (M3.3a), or an image with the `graphics` feature lacks `vmwgfx` in its slot's modules or Mesa's svga driver (the string `vmwgfx` in `libgallium-*.so` or the DRI directory) in its slot (M3.6); and, for each `out/*.graphics-nvidia.ext4.gz`, fails when the image's slot holds `nouveau`, or the pack lacks it, its `lib/modprobe.d/nouveau.conf` turning GSP on, or keeps more than one GSP release (M8.39a) | `sudo` to read the root-owned `out/work/`, `cpio` and `zstd` (CI installs both with QEMU), `debugfs` to read the pack |

## The A/B test's steps

The A/B steps run inside the VM from the OpenRC service `ab-test/files/etc/init.d/edel-ab-test` (a committed runlevel link enables it; it needs `edel-boot-ok`). It keeps its step number in `ab-test-step` on the EFI system partition and downloads every update from `http://10.0.2.2:8000/`. On a boot with a second disk (the install test's live boot) the service does nothing. Step 1 checks the read-only root, `softlockup_panic=1` in `/proc/cmdline` and `0` in `/proc/sys/kernel/softlockup_panic` (the guard turned the lockup panic off once it confirmed the slot, M6.17), expects `refused: expired` for `expired.toml` and `refused: signature` for `bad.toml` (every `edel update` there passes `--allow-http`, M3.8), sets `addons.installed` to `ci-hello` and `ci-gone`, expects `refused: add-on ci-hello does not match` for `badaddon.toml` with slot B left off, and wants the real update to say `add-on ci-gone is not in` (M7.2a), writes markers into `/home` and `/var`, deletes `/var/lib/ci-new`, changes the hostname with `edel settings set` and `apply`, notes the ssh host key, adds a user, drops a system user from the machine's `/etc/passwd` and installs into slot B; step 2 expects all of that kept, the add-on's `/usr/bin/ci-hello`, `/etc/ci-hello.conf` linked, its service in the default runlevel and its greeting in `/run/ci-hello`, and `edel status`'s `hardware:` line for ci-hang's pack and none for ci-hello's (M7.11, the packs file written at that boot), slot B still the signed image byte for byte (the first `size` bytes of its partition hash to `release.toml`'s `sha256`, after it booted) and its file system its shrunk size (`df -m /` under 1024, as slot A's in step 1, M1.12), `edel.tag=ci` in `/proc/cmdline` (slot B's first boot ran by its own `slot.cfg` under slot A's loader, M6.17), its tagged boot loader on the ESP with `BOOTX64.EFI.prev` kept, the dropped system user and `/var/lib/ci-new` back from the slot, and restarts into slot B once more; step 2b expects the greeting again at slot B's second boot, when nothing is applied and OpenRC read the services before the `/etc` layer came (`edel-data` has it read them again, M7.2a), then (M7.2b) sets `addons.installed+=virtualization` and `addons.installed+=printing` (M7.6d) and applies, which must say both start at the next restart, and restarts; step 2c expects `qemu-img`, qemu in the `kvm` group, the add-on in the version's folder and nothing pending, and printing's `scanimage -L` saying `No scanners were identified`, SANE's `dll.d/airscan` and `edel addon list` saying printing is installed, then chooses `ci-hang`, whose service never finishes starting, applies and restarts; step 2d expects slot B running without `ci-hang` after the guard's restart, `addons = ["ci-hang"]` in `last-fallback.toml`, `ci-hang` in the version's `failed` list and `edel addon list`, and `qemu-img` still there, takes `ci-hang` out and rolls back to slot A by command; step 3 expects the markers and slot A's loader back on the ESP, none of the add-ons' files (no `qemu-img`), link or service, installs into slot B again and breaks its initramfs; step 4 expects `B: ok=0 try=3`, the markers and `from = "B"` in `/data/edel/last-fallback.toml`, checks that a rollback to slot B is refused and installs slot B again with its own `slot.cfg` pointing its root at a partition that does not exist; step 4b (M6.17) expects slot B off again (`ab-test.sh` wants the initramfs's `Mounting root: failed` and the kernel's `Attempted to kill init` on serial: under `panic=` Alpine's initramfs exits instead of waiting in its rescue shell) and installs slot B again with a service that hangs and without its watchdog drivers (`lib/modules/*/kernel/drivers/watchdog/` emptied, softdog included, as linux-lts has one, and softdog taken out of `slot.cfg`'s `modules=`), so it boots with no watchdog at all; step 5 expects slot B off after the guard restarted it itself (M1.10; `ab-test.sh` wants the guard's `restarting the computer now` on serial) and installs it again with a service that freezes the kernel with panic reboots off once the guard pets the hardware watchdog (its `state` is `active`; udev loads i6300esb late in the boot); step 6 expects slot B off again and installs it again with the health check `network` added to its os-release, a service that writes `$health_dir/network` once a default route exists, and neither its networking service nor this test's; step 7 expects slot B off again (M1.11; `ab-test.sh` wants the guard's `health not reached after N s: network`), installs slot B once more with the same unreachable `network` check and a watcher service, and sets `A_TRY=3`, so no slot has a try left (M6.17); in step 8 slot B's guard must stand down (`ab-test.sh` wants its `no version has a start left, so the computer keeps running` on serial), and the watcher, which fails when slot B boots a second time (a mark on `/data`), waits for `$no_healthy_slot`, then 45 s, and prints `AB-TEST: PASS` when slot B still runs and `edel status` has its `health:` line, then powers off. Step 4 proves GRUB's count of three tries; for the hang and freeze cases the test sets `B_TRY=2` in the ESP's `grubenv` after installing (the same length, so the block stays 1024 bytes), so each takes one try, about 170 s less per run. The install test image and the A/B update are built with `--health-timeout 30`. A mismatch prints `AB-TEST: FAIL: step N expected "LINE"` and powers off.
