# Image definitions

An image definition is a TOML file here; `edel image build` turns it into an image. Since M4.0 a definition lists features (`features/NAME.toml` at the repository root, [docs/FEATURES.md](../docs/FEATURES.md)) and holds only image facts; packages, services, kernel modules, mkinitfs features, health files and files come only from the features. The schema, the feature lookup and the merge are in `crates/edel/src/def.rs`, the feature file reader in `features.rs`, the build steps in `image.rs`. Two exist for release, both format 2, Alpine `v3.24` (`main` and `community`), `x86_64`:

- `container.toml`: `edel-container`, features `base`, `container`; no hostname, no services, no `[vm]`; packed as `out/edel-container-x86_64.tar.gz` (load it with `docker import`).
- `edel.toml` (M8.17): `edel`, the one disk image for every machine, servers, VMs, desktops and laptops, and the stick to try and install from. Its features are the list in the file: the desktop's, plus `kernel` (linux-lts and the CPU microcode), `udev` for device events (eudev, which libinput and the compositor read; mdev is gone) and `ssh`, switchable. Hostname `edel`, `off = ["ssh"]` (openssh-server installed, sshd started only where the settings file says so), `addons` (`fonts-cjk`, `orca`, `printing`, `containers`, `virtualization`, M7.2a), and `[vm]` with kernel `lts`, `slot_mib = 1536` so the disk fits a common 8 GB stick (`edel install` gives the machine 4096 MiB slots), and `console=tty0 console=ttyS0,115200`. Packed as `out/edel-x86_64.img` (GPT disk: EFI system partition, slot A filled, slot B empty, and a 64 MiB `edel-data` partition that grows to the end of the disk on first boot) and `out/edel-x86_64.ext4` (one slot cut to its file system with `resize2fs -M`, the update image), each also as `.gz`. A machine with no graphics card starts none of the `screen` features' services (`seat`, `login`, `compositor`, `power`, `bluetooth`), and its guard waits for none of their health, so the same image runs as a server; a machine with a screen starts the desktop (greetd's greeter, below). Its variant is `vm`: a bootable A/B disk, which is all a variant decides today.
- CI's `ci/vm/vm.toml` (`edel-vm`, `ci/` only, never released) is the image of edel's own tests that need no screen: the system, developer mode, fleet, install and A/B tests boot it many times, with `console=ttyS0` and 4096 MiB slots. The release image is the one the boot test boots with no screen and the desktop test boots with one.
The laptop image, a text console for sticks (M3.3a), was dropped on 2026-10-06 at Alimardon's word, as the desktop does its job; the `kernel` feature's `why` says why one kernel, linux-lts, serves every machine. greetd's greeter is our compositor running the text greeter `agreety` in foot on VT 7 (M4.7b); it asks for the user and starts `dbus-run-session -- edel-compositor` as them (M4.2b), and greetd brings the greeter back whenever a session ends, a crashed one included, until the compositor greets people itself (M5.10); Ctrl+Alt+F1 reaches the text console.

Check a definition with `cargo run --quiet --locked -- image check images/edel.toml` (it prints `<name>-<arch>: ok (<n> features, <m> packages)` and checks every feature file strictly); list its build steps with `cargo run -- image build images/edel.toml --plan`.

## Schema (strict: an unknown key fails)

- Top level: `format = 2` (format 1 is refused), `name`, `variant` (`"container"` or `"vm"`), `arch`, optional `hostname`, `features` (names, merged in this order), optional `off` (switchable listed features shipped with their services off, written as `EDEL_SERVICES_OFF`), optional `addons` (features with `addon = true` built beside the image from its root, M7.2a, [FEATURES.md](../docs/FEATURES.md#add-ons-m72a): `edel`'s `fonts-cjk`, `orca`, `printing`, `containers` and `virtualization`; a container image has none, and `edel image build --no-addons` leaves them out of a test image). Outputs are named `<name>-<arch>`.
- No `[alpine]`: the Alpine branch, mirror, repositories and build container digest are the `base` feature's (`features/base.toml`), the one place they are written (M5.27); a definition that names them is refused, and so are two features that do.
- `[vm]`, required for `vm` and forbidden for `container`: `kernel` (the Alpine kernel flavour; a listed feature must install `linux-<kernel>`), `slot_mib` (at least 64), optional `cmdline` (never `modules=`: the build writes `modules=` from the features' `modules`, adds `boot::WATCHDOG_ARGS`, loads any `/boot/intel-ucode.img` and `/boot/amd-ucode.img` before the initramfs, and rebuilds the initramfs with the features' `initramfs`), optional `data_mib` (default 64, at least 16).
- `[image]`, optional: `health_timeout` (seconds, default 120, at least 10), written into os-release as `EDEL_HEALTH_TIMEOUT` beside `EDEL_HEALTH`, the union of the features' `health` (an image with variant `vm` needs one; `ab-boot` has `default-runlevel`); `edel image build --health-timeout` overrides it for test images. Every slot carries its boot loader (GRUB binary, `grub.cfg`, `loader.toml`) and `slot.cfg`, how GRUB starts that slot (M6.17), in `/usr/lib/edel/boot/`; `--loader-tag` makes a test loader differ and puts `edel.tag=TAG` on the slot's command line. Every image's os-release gets the build's `VERSION_ID` (`edel image build --version`, numbers joined by dots; without it the overlay's `0.1` stays), `EDEL_CHANNEL` (`--channel`, default `dev`), `EDEL_ARCH` and `EDEL_PLATFORM_LEVEL` (0 until M8.8), the installed packages land in `/usr/share/edel/packages` and `out/<image>.packages` (M3.1), and each listed feature's file in `/usr/share/edel/features/`. `vm` images also get `EDEL_LOADER_VERSION` and `EDEL_IMAGE="<name>-<arch>"`, the name `release.toml` lists their image under, and `EDEL_HOSTNAME`, the hostname `edel settings apply` goes back to when the settings file names none.
- `[release]`, optional: `public_keys`, key files (relative to the definition) copied to `/usr/share/edel/keys/` in `vm` images; `edel image build --public-key FILE` adds more for test images. No definition names a key until Alimardon makes the release key (`docs/RELEASE.md`); its public half then goes to `images/keys/edel-release.pub` and into every definition.
- `name` and `hostname` use only a-z, 0-9 and `-` and do not start with `-`. `cmdline` is pasted into `grub.cfg` and `slot.cfg`, so it may not contain `"`, `'`, `\`, `$`, `;`, `{`, `}`, `#` or a backtick.
- The code accepts `aarch64` for a VM, but no aarch64 definition exists until M9 and CI builds only `x86_64`.

## Rules

- A new package or service goes into a feature, with its reason in the feature's `why` (principle 3; the build refuses a feature without one). Keep `e2fsprogs-extra` in `ab-boot`: it gives `edel update` its `tune2fs`, and the A/B test failed without it. Keep `libgcc` there too: the `edel` that Alpine's cargo builds links against `libgcc_s.so.1`.
- A program of ours (`edel-compositor`, later shell-ui and Settings) goes into a feature's `programs`; `edel image build` copies it from beside itself, so `ci/build.sh` builds the whole workspace first, and the feature lists the libraries it links in `packages` (`readelf -d` shows them), because apk does not see a copied program.
- A service in a feature's `[services]` is linked into its runlevel and needs `/etc/init.d/NAME` from a package or a feature's directory, or the build fails. Release images enable services only through features, never through committed runlevel links.
- Each feature's `features/NAME/` is copied over the image with `cp -R` in the order the definition lists the features, after packages and before services; no file may be shipped by two features. Copies are owned by root and keep their git mode, so commit scripts and init scripts as executable (100755; `git ls-files -s` shows it).
  - `base/` (every image): the identity. `usr/lib/os-release` is required (`NAME="Edel OS"`, `PRETTY_NAME="Edel OS 0.1 (development)"`, which the build replaces with the release's version); the build makes `/etc/os-release` a link to it. Also `etc/issue` (`Welcome to Edel OS`, no version, since the build does not rewrite it) and `etc/motd`.
  - `ssh/`: `etc/conf.d/sshd`, Alpine's file with `key_types_to_generate="ed25519"`, so the first boot makes one host key in milliseconds instead of an RSA key that takes a random, sometimes long time.
  - `machine/`: `etc/inittab` (adds a getty on the serial console `ttyS0`), `etc/network/interfaces` (lo, and eth0 by DHCP). Device events are a feature of their own: `udev` (eudev), which `edel` lists; the busybox mdev feature is gone (M8.17).
  - `seat/` (desktop, M4.1): the `edel-rundir` boot service, which makes `/run/edel/session` (mode 0770, group `seat`, no sticky bit since M4.7b, so the greeter's compositor and the person's replace each other's files) for the files the session leaves for root, such as the compositor's health file `ready` (M4.8), while `/run/edel` stays root's alone; `etc/conf.d/seatd` runs seatd under supervise-daemon.
  - `login/` (desktop, M4.1): `etc/greetd/config.toml` (on VT 7, `edel-compositor -- edel-shell-ui --greeter --cmd /usr/libexec/edel-session` as user greetd, M4.7b, M5.10b: shell-ui's greeter on our compositor, starting the person's compositor after login, M4.2b), `etc/pam.d/greetd` (Alpine's file plus `session optional pam_rundir.so`, so every session gets `/run/user/UID` at 0700 without logind), `etc/conf.d/greetd` (supervise-daemon).
  - `laptop/` (the desktop, M3.4): the `edel-report` service, which runs `edel report --esp` once per boot after `edel-boot-ok`; on a removable or USB disk it writes `EFI/edel/report.toml` in place (never through a rename on FAT), and on an installed laptop it writes nothing, so the stick carries the report for a person with no login yet (`docs/TRY-IT.md`).
  - `ab-boot/`: `etc/fstab` (root is whichever slot GRUB started, mounted read-only); the `edel-data` sysinit service (`edel boot mount-data`: grow partition 4 on first boot, mount it at `/data`, add new system users from the slot to the machine's account files, overlay `/etc` with its upper layer on `/data`, top up `/data/var` from the slot, bind `/data/home`, `/data/var` and `/data/root` over `/home`, `/var` and `/root` (root's home starts as a copy of the slot's, mode 0700), and mount `/tmp` as tmpfs) the `edel-guard` sysinit service (`edel boot guard` in the background: pets the watchdog until the health files exist, then confirms the slot and exits), the `edel-settings` boot service (`edel settings apply --boot` under busybox `timeout 60`, so one stuck step never stops the boot, before `hostname`: seeds `/data/edel/settings.toml` on first boot and applies its hostname, users, ssh keys and developer mode), and the `edel-boot-ok` OpenRC service, which touches `/run/edel/default-reached` last in the default runlevel and prints the guard's confirmation, the version line and `Started in N s, M MiB of memory in use, R MiB used on the root` (the budgets read it, M3.2). If the health files never appear, the watchdog restarts the machine and GRUB gives the slot three tries and then starts the other slot if that one is OK; if no slot is OK with tries left, it starts the first slot in ORDER anyway. `edel image build` copies itself to `/usr/bin/edel` in every `vm` image (the path M6.5's doas rule names).
- ADR-006 aims for OS defaults under `/usr` and an `/etc` that holds only what an administrator changed. Today only `os-release` follows it; `etc/issue`, `motd`, `fstab`, `inittab`, `network/interfaces` and the init scripts still live in `/etc`. They move only in a roadmap step (M1.4 notes: "later, our own defaults move to `/usr`"), never as a side change.
- The build locks root's password (`*`); access comes later from keys or the settings file. Never ship a user or a default password (ADR-008).
- CI greps text from the features: `Welcome to Edel OS` (`base/etc/issue`), a `PRETTY_NAME` starting `Edel OS `, the hostname `edel` (`edel login:`), `Starting sshd` (only once the settings file turns `services.ssh` on, as the boot test's console key does) and the `edel update` output. Change them only together with the `ci/` scripts.
- Test-only files and CI-only definitions and features never go here or in `features/`: they live under `ci/` and reach a test image through `--files` or a definition under `ci/` with its own `features/` beside it.
- Shell code in the features is busybox POSIX sh: `#!/bin/sh` (or `#!/sbin/openrc-run`), `set -eu` in scripts, tabs.

## Coming changes (roadmap)

Make each change only in its step, and take the details from the step itself, not from here. Steps that touch this directory:

- The image's health with a screen is `default-runlevel compositor` (M4.8: `health = ["compositor"]` in `features/compositor.toml`): its guard waits for `/run/edel/session/ready`, which the greeter's compositor writes. With no graphics card the guard waits for `EDEL_HEALTH_SCREEN` instead of that file (M8.17), which is the health of the `screen` features no other feature lists.
- Definitions stay strict in every format.
